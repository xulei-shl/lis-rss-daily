# 多用户角色扩展方案 — 实施步骤与验证

## 实施顺序

### Step 1：数据库迁移
- 编写 SQL 迁移脚本，创建 `source_subscriptions` 和 `user_articles` 表
- 编写数据迁移脚本：存量文章 → admin 绑定，存量源 → admin 订阅
- 补齐所有日志表 `user_id` 字段：`article_filter_logs`、`article_process_logs`、`email_fetch_logs`（严重泄露）、`journal_crawl_logs`、`keyword_crawl_logs`
- 添加 `rejected_articles.user_id` 字段
- 创建索引
- **验证**：确认迁移后数据完整，admin 可见所有存量文章

### Step 2：Auth 中间件
- 扩展 `UserRole` 类型
- 更新 `ROLE_HIERARCHY`
- 新增 `requireUser` 中间件
- 更新 `effectiveUserId` 逻辑
- **验证**：admin/user/guest 三种角色登录后 `effectiveUserId` 正确

### Step 3：路由权限调整
- 逐一审查所有 route 文件，替换 `requireAdmin` 为 `requireUser`（用户级操作）
- 保留 `requireAdmin` 仅用于系统级操作
- 更新 `web.ts` 页面路由条件
- **验证**：guest 不能写操作，user 可以对源/提示词/主题等 CRUD，admin 可以做全部操作

### Step 4：文章查询重构（核心）
- 替换 `src/api/services/articles.ts` 中 4 路 OR JOIN 为 `user_articles` JOIN
- 逐一替换其他受影响文件中的查询
- **特别关注总结系统**：`daily-summary-repository.ts` 中的 `getDailyPassedArticles`、`getAllJournalArticles`、`getInsightsArticles`，以及 `daily-summary-generator.ts` 中的 `generateSearchSummary`
- **验证**：admin 可见所有文章，user 仅见自己订阅的文章，guest 可见 admin 文章

### Step 5：抓取流程添加关联步骤
- 在 `saveArticles()` 后添加 `linkArticlesToSubscribedUsers()`
- 修改各调度器（RSS/期刊/关键词/Gmail）的 fetch 流程
- 添加源创建时自动订阅逻辑
- **验证**：用户 A 抓取后，所有订阅同一源的用户都能看到新文章

### Step 6：过滤管道重构
- `filterArticle()` 写入 `user_articles` 而非 `articles`
- `batchUpdateFilterStatus()` 增加 `userId` 参数
- `triggerAutoFilter()` 只对触发用户执行
- **验证**：用户 A 拒绝的文章，用户 B 仍可见（pending），双方互不影响

### Step 7：清理调度器重构
- 重写 `rejected-cleanup-scheduler.ts` 查询和清理逻辑
- 清理只删除 `user_articles` 行，零引用时物理删除文章
- 归档增加 `user_id` 字段
- **验证**：清理后用户 A 的文章消失，用户 B 的文章仍在

### Step 8：总结系统适配
- 替换 `daily-summary-repository.ts` 中 3 个文章查询函数使用 `user_articles`
- 修复 `generateSearchSummary` 缺失的 email_sources 校验
- 调度器：`daily-summary-scheduler.ts` 和 `insights-scheduler.ts` 从默认 userId=1 改为遍历所有活跃用户
- `related-scheduler.ts`、`telegram/bot-manager.ts` 中的硬编码 userId=1 逐一修复
- **验证**：各用户生成的总结只包含自己可见的文章

### Step 9：日志查询重构
- 全部 7 个日志查询文件将 JOIN 模式改为 `user_id` 直接过滤
- 重点修复 `email-fetch-logs.ts` 的严重泄露（当前无任何用户作用域）
- 修复 `unified-logs.ts` 中 email 日志未传 userId 的问题
- 前端日志页面 `filter-logs.ejs` 确认数据隔离正确
- **验证**：各用户只能看到自己订阅源产生的日志

### Step 10：UI 适配
- 更新 `layout.ejs`、`articles.ejs`、`index.ejs` 模板
- 更新 `web.ts` 页面路由条件
- **验证**：user 角色看到操作按钮和设置/主题入口，guest 看不到

## 风险与注意事项

1. **性能**：`user_articles` 表可能增长到与 `articles` 同量级（每用户 × 每篇文章），需监控查询性能，必要时优化索引
2. **并发**：多个用户同时抓取同一源时，`linkArticlesToSubscribedUsers` 的 `onConflict().doNothing()` 确保不重复
3. **调度器硬编码 userId=1**：`daily-summary-scheduler`、`insights-scheduler`、`related-scheduler`、`telegram/bot-manager` 均硬编码 `userId=1`。Step 9 需逐一修复为遍历所有活跃用户，或按需指定
4. **过滤性能**：多用户场景下，每篇文章的过滤在首次抓取时只对触发用户执行，其他用户保持 `pending`。可考虑添加定时任务补齐
5. **向量搜索**：ChromaDB 中的 embedding 是文章级别的，搜索时需额外过滤 `user_articles` 确保只返回用户可见的文章
6. **总结数据快照**：`daily_summaries.articles_data` 存的是 JSON 快照，生成后不会随文章状态变化而更新。这是设计预期（历史总结保持历史状态），无需改变
