# 多用户角色扩展方案 — 整体设计

> 本文档描述在现有 `admin` / `guest` 双角色基础上，新增 `user` 角色的完整方案，包括数据模型、权限体系、核心逻辑重构、UI 适配及迁移步骤。

## 目标

新增角色 `user`，具备以下能力：

- 自定义添加订阅源（RSS / 期刊 / 关键词 / Gmail）
- 管理系统提示词
- 管理 LLM 配置
- 管理通知（Telegram / 企业微信）
- 管理主题领域及其关键词
- 查看、检索、操作自己账号下的文章
- 不同用户可添加相同信息源，获取相同文章
- 文章拒绝/已读状态为 per-user，互不影响

## 角色定义

| 角色 | 级别 | 读取权限 | 写入权限 | 数据范围 |
|------|------|---------|---------|---------|
| `admin` | 3 | 所有数据 | 全部操作 | 自身数据 |
| `user` | 2 | 所有数据 | 用户级操作 | 自身数据 |
| `guest` | 1 | admin 数据（effectiveUserId=1） | 无 | 只读 admin 数据 |

## 核心概念

### 源共享

源（RSS / 期刊 / 关键词 / Gmail）为**全局实体**，不再绑定单个用户。用户通过 `source_subscriptions` 表建立订阅关系，决定哪些源对哪些用户可见。

### 文章多用户关联

文章为**全局实体**（去重不变），通过 `user_articles` 表维护每用户状态。不同用户对同一篇文章可有不同的 `filter_status`、`is_read` 等状态。

### 拒绝/清理 per-user

拒绝状态存储于 `user_articles`，清理只删除该用户的状态记录，文章本身在所有用户都不再引用时才物理删除。

## 现有 per-user 组件（表已有 `user_id`，仅需调权限）

以下组件的数据模型**已经按用户隔离**，多用户场景只需将路由从 `requireAdmin` 改为 `requireUser`：

| 组件 | 表 | user_id | 说明 |
|------|----|---------|------|
| 系统提示词 | `system_prompts` | ✅ 已有 | 每个用户管理自己的提示词模板 |
| LLM 配置 | `llm_configs` | ✅ 已有 | 每个用户配置自己的 API key、模型、provider |
| 主题领域 | `topic_domains` | ✅ 已有 | 每个用户定义自己的主题分类 |
| 主题关键词 | `topic_keywords` | ✅ 已有 | 每个用户定义自己的关键词 |
| 通知设置 | `settings` | ✅ 已有 | 每个用户的 Telegram/通知开关 |
| Telegram 聊天 | `telegram_chats` | ✅ 已有 | 每个用户绑定自己的聊天 |
| 微信 Webhook | `wechat_webhooks` | ✅ 已有 | 每个用户配置自己的 Webhook |
| 每日总结 | `daily_summaries` | ✅ 已有 | 每个用户独立生成和查看 |
| 深度检索 | `deepsearch_tasks` | ✅ 已有 | 每个用户独立的检索任务 |

## 需要重构的组件

以下组件需要数据模型改造才能支持多用户：

| 组件 | 当前问题 | 改造方式 |
|------|---------|---------|
| RSS 源 | 通过 `user_id` 作作用域隔离 | 改为全局 + `source_subscriptions` |
| 期刊源 | 同上 | 同上 |
| 关键词订阅 | 同上 | 同上 |
| Gmail 源 | 同上 | 同上 |
| 文章状态 | 全局 `filter_status`/`is_read` | 迁移到 `user_articles` |
| 过滤日志 | 无 `user_id` 或 JOIN 遗漏 | 补齐 `user_id` + 直接过滤 |
| 处理日志 | 同上 | 同上 |
| 抓取日志 | 部分无 `user_id`（email 泄露） | 补齐 `user_id` |
| 调度器 | 硬编码 `userId=1` | 遍历所有活跃用户 |
