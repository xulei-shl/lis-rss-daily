# 多用户角色扩展方案 — 通知推送系统适配

## 1. 通知路径总览

| 触发点 | 文件 | Telegram | 微信 |
|--------|------|----------|------|
| 文章完成流水线处理 | `pipeline.ts` | `sendNewArticle(userId, article)` | 无 |
| 每日摘要定时任务 | `daily-summary-scheduler.ts` | `sendDailySummary` / `sendJournalAllSummary` | 同左 |
| 洞察定时任务 | `insights-scheduler.ts` | `sendInsightsSummary` | 同左 |
| PDF 摘要生成 | `pdf-summary.routes.ts` | `sendPdfSummary` | 同左 |
| 手动 API 触发 | `api/daily-summary.ts` | `sendDailySummary` / `sendJournalAllSummary` / `sendInsightsSummary` | 同左 |

## 2. Telegram 推送分析

### 当前架构

- **BotManager** (`telegram/bot-manager.ts`): `getEnabledUserConfigs()` 硬编码 `userId = 1`，只为 admin 启动机器人实例
- **TelegramBot** (`telegram/bot.ts`): 每个实例绑定一个 `userId` + 该用户的 `telegram_chats` 列表
- **Notifier** (`telegram/index.ts`): 以 `userId` 为参数，从 `telegram_chats` 表查询该用户的聊天列表，使用该用户的 `bot_token` 发送

### 多用户场景问题

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| BotManager 只启动一个用户的机器人 | **高** | 非 userId=1 的用户无法使用交互式机器人 |
| 长轮询 update_id 冲突 | **高** | 同一 bot token 启动多个实例，update_id 持久化文件会冲突，导致消息丢失 |
| 调度器默认 userId=1 | **中** | 每日总结/洞察调度器通过 `DAILY_SUMMARY_USER_ID` / `INSIGHTS_USER_ID` 环境变量指定，默认 1 |
| 流水线管道正确传递 userId | **低** | `processArticle(articleId, userId)` 的 userId 来自调用者（爬虫调度器），非硬编码 |

### 改造方案

#### 方案 A：单用户模式（推荐初始阶段）

**原则**：通知系统继续为 admin 服务。user 角色的通知通过页面查看，不通过 Telegram。

改动：
- BotManager 的 `getEnabledUserConfigs()` 改为查询所有 `role = 'admin'` 的用户，而非硬编码 userId=1
- 每个 admin 用户可独立配置自己的 bot token 和聊天列表
- 调度器（daily-summary/insights）改为遍历所有 admin 用户，各自生成并推送

```typescript
// bot-manager.ts 改造
async function getEnabledUserConfigs(): Promise<UserConfig[]> {
  // 查询所有 admin 用户，每个用户独立配置 bot token
  const admins = await db.selectFrom('users')
    .select(['id', 'username'])
    .where('role', '=', 'admin')
    .execute();

  const configs: UserConfig[] = [];
  for (const admin of admins) {
    const enabled = await getSetting(admin.id, 'telegram_enabled');
    const botToken = await getSetting(admin.id, 'telegram_bot_token');
    if (enabled === 'true' && botToken) {
      const chats = await getTelegramChats(admin.id);
      configs.push({ userId: admin.id, botToken, chats });
    }
  }
  return configs;
}
```

#### 方案 B：多用户扩展（长期）

所有角色（admin / user）均可使用 Telegram 通知：
- 每个用户独立配置自己的 bot token 和聊天列表
- 不同用户使用**不同的 bot token**（避免长轮询冲突）
- BotManager 遍历所有启用了 Telegram 的用户

## 3. 微信推送分析

### 当前架构

- Webhook 配置来源：`config/wechat.yaml` 文件
- 管理接口：`/api/wechat/webhooks` CRUD（全局，不按用户隔离）
- 查找逻辑：`getWebhooksForPushType(pushType)` — 返回所有匹配的 webhook，**无 userId 过滤**
- 消息发送：`sendByPushType(userId, type, data)` — 接受 userId 但**仅用于日志和去重缓存，不用于路由**

### 多用户场景问题

| 问题 | 严重程度 | 说明 |
|------|---------|------|
| Webhook 全局共享 | **高** | 所有 webhook 收到所有用户的通知，数据会混合 |
| 无 userId 路由 | **高** | 无法区分"用户 A 的通知发到 webhook X，用户 B 的发到 webhook Y" |
| 配置来自 YAML 文件 | **中** | 运行时通过 API 修改的配置存于 `wechat_webhooks` 表，但 `wechat-config.ts` 读取 YAML 文件，两者可能不一致 |

### 改造方案

#### 方案 A：全局模式（推荐初始阶段）

**原则**：微信通知保持全局，仅 admin 可配置 webhook。user 角色不涉及微信推送。

改动：
- 管理接口保留 `requireAdmin` 权限
- 调度器生成摘要时，向所有 webhook 推送 admin 用户的数据
- 在消息内容中标注来源用户（如 `【用户A】每日总结`）

#### 方案 B：按用户隔离（长期）

- `wechat_webhooks` 表增加 `user_id` 字段（可空，null 表示全局 webhook）
- 查找逻辑：`getWebhooksForPushType(userId, pushType)` — 同时匹配全局 webhook 和该用户专属 webhook
- 管理接口允许 user 角色创建自己的 webhook（需 `requireUser` 中间件）
- 配置文件 `wechat.yaml` 保持全局，API 管理的 webhook 支持按用户隔离

## 4. 调度器 userId 修复清单

| 调度器/服务 | 文件 | 当前行为 | 改造方案 |
|------------|------|---------|---------|
| 每日总结调度器 | `daily-summary-scheduler.ts` | `DAILY_SUMMARY_USER_ID` 默认 1 | 遍历所有活跃用户（有订阅源的用户） |
| 洞察调度器 | `insights-scheduler.ts` | `INSIGHTS_USER_ID` 默认 1 | 同上 |
| 相关文章调度器 | `related-scheduler.ts` | `const userId = 1` | 改为遍历所有订阅源用户的文章 |
| BotManager | `telegram/bot-manager.ts` | `const userId = 1` | 见上文 Telegram 方案 |
| 关键词抓取 | `api/keywords.ts` | `const userId = 1` | 使用调用者传入的 userId |

## 5. 实施顺序

### Step 1（初始阶段，推荐）
- 通知系统保持为 admin 专属
- BotManager 改为查询所有 admin 用户（不再硬编码 userId=1）
- 调度器遍历所有 admin 用户生成摘要和推送
- 微信保持全局模式

### Step 2（长期扩展）
- 支持 user 角色独立配置 Telegram bot
- 微信 webhook 增加 `user_id` 字段支持按用户隔离
- user 角色可创建自己的 webhook 配置
