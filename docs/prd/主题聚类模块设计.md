## 1. 背景与目标

当前系统已具备：RSS/期刊/关键词/邮件/网页抓取 → LLM 过滤 → 翻译与向量化 → 全文总结（AI 摘要）→ 每日与周期总结。但**全文总结之后没有主题级结构**，无法回答「这个方向有哪些研究角度」「脉络怎么演进」「趋势如何」「空白在哪」。

本模块的目标：**对已有全文总结的文章做主题聚类，并对每个主题产出可追溯、可检索的多维度分析**，供所有登录用户（含 guest）在 Web 端查看与检索。

### 1.1 交付的四种能力（用户目标）

| 能力 | 含义 | 定位 |
|---|---|---|
| **研究角度** | 同一主题下文章分化的不同切入角度 | 簇内子群 |
| **研究脉络** | 同一角度上文章的承接与演进（问题→方法→发现） | 簇内时间链 |
| **研究趋势** | 角度/脉络随时间的消长与方法迁移 | 周期指标 |
| **研究历史** | 该主题文章的时序清单与各自贡献点 | 时间轴 |

### 1.2 一条不可回避的诚实边界

系统内**没有引文/参考文献数据**（全文总结为 AI 生成的摘要，不含 references）。因此「脉络/延续性」是**基于研究问题、方法、研究对象的语义与结构相似度推断**得出的，**不是引文网络，也不是真实的学术传承关系**。

> **硬性要求**：前端在「研究脉络」版块必须显式标注口径，例如「基于语义与方法相似度推断的研究脉络，非引文关系」。禁止让用户误认为是引用关系。

## 2. 范围

### 2.1 本模块包含

- 仅针对 **有全文总结（`articles.ai_summary` 非空）** 的文章。
- 主题的持久化身份、增量归属路由、游离池孵化。
- 簇内：研究角度分群、时间串链（脉络）、周期指标、研究历史。
- 每主题的多维分析（脏标记增量预计算落库）。
- 面向全部登录用户的只读页面与检索接口。

### 2.2 明确不做（本期）

| 不做项 | 原因 |
|---|---|
| 主题之间的血缘（merge/split 事件流） | 用户已明确不需要；当前量级下自动判定误判率高 |
| 每天全量重跑聚类 | 主题漂移、成本爆炸（需求文档已警示） |
| 页面访问时实时调用 LLM | 响应超时；必须脏标记预计算 |
| 日级趋势曲线 | 单主题月均新增 3~5 篇，日级噪声大于信号 |
| 自动 split/merge 无人确认 | 见上；若未来需要，另立需求 |
| **任何人工干预入口**（文章级排除/移动、主题级合并/拆分/归档） | 本期全自动；仅在架构上预留零冗余扩展点（见 §13.4） |
| 改 `articles` 表加聚类字段 | 该表历史上被重建 3 次（023/034/041），且属热点表 |

## 3. 设计原则

1. **确定性规则前置，LLM 只做语义收敛。** 角度、链条、指标、矩阵全部由规则算出；LLM 只负责命名与叙述，且输出必须可回链到具体 `article_id`。（做法来自参考项目 `ai-enrichment.ts`）
2. **任何 LLM 输出都必须过 schema 校验 + 占位符拒绝 + 引用白名单 + `input_hash` 审计。** 校验失败即标记失败，**不写入占位内容、不伪装成功**。
3. **样本不足必须显式降级**，不允许用不足样本输出确定结论（参考项目 `evaluate.ts` 的 `measured / insufficient_data` 双态）。
4. **零新增运行时依赖。** 不使用 UMAP/HDBSCAN：当前规模（数百篇、日增个位数）下，纯 TypeScript 的质心路由 + 阈值凝聚聚类足以胜任，且可单测、可复现、无 Python 微服务运维成本。连接方式取**平均连接**而非单链：单链只要存在一条桥接对就会把两个不相干的簇并成一个（实测 θ=0.65 时单链产出 25 篇的簇，簇内最小两两仅 0.47；平均连接同期只产 12 篇且最小两两 0.58）。
5. **不改动既有的过滤/翻译/向量化/总结流水线**，本模块是完全增量的旁路。
6. **多归属而非二选一。** 一篇文章可以归属多个主题（有上限约束），用链接表表达；同时用「主归属」固定计数口径，避免统计歧义（§6.0）。
7. **主题集合版本化，身份不可变。** 全量重聚类不就地覆盖，而是产生新版本、旧版本归档保留，保证旧 URL 与旧分析不失效（§7.9）。

## 4. 现状与约束（实测，2026-09-29）

### 4.1 数据规模

| 指标 | 实测值 |
|---|---|
| articles 总数 | 6299 |
| passed + completed | 2553 |
| **有全文总结（`ai_summary` 非空）** | **817**（815 为 passed） |
| 全文总结平均长度 | 2864 字符（最长 9811） |
| 月增全文总结 | 42 ~ 170（2026-02→09） |
| 近 14 天日增 | 1 ~ 8 篇，多数 1~4 篇 |
| `created_at` 跨度 | 2026-02-12 → 2026-09-28（8 个月） |

### 4.2 时间字段可用性（关键）

| 来源 | 篇数 | `published_at` | `published_year` | 时间精度 |
|---|---|---|---|---|
| rss | 668 | 664 | 0 | **日级** |
| email | 59 | 59 | 0 | **日级** |
| journal | 89 | 0 | 89 | **仅年级** |
| keyword | 1 | 0 | 1 | 仅年级 |
| **合计** | **817** | **723** | **90** | 混精度 |

> 结论：时间维度**可行**，但必须携带精度标记。混合日级与年级数据而不加标记，会静默产生假趋势。

### 4.3 向量现状

- Chroma 运行中，collection `articles`，cosine，**dim = 1024**（模型 `BAAI/bge-m3`），记录数 857。
- **全文总结未被向量化**：`buildVectorText()`（`src/vector/text-builder.ts`）只取 `title_zh / summary_zh / markdown_content || content`，不含 `ai_summary`；`updateArticleAiSummary()`（`src/api/articles.ts:1789`）只更新列，不触发重新索引。
- 向量覆盖率仅约 1/3（857 / 2553），且与全文总结集合只部分重叠（817 中有 473 已向量化）。

> 结论：**本模块不复用现有向量**，为「切面文本」单独生成 1024 维向量并自存。

## 6. 数据模型

> 迁移文件：`sql/045_add_topic_cluster.sql`（同时需在 `scripts/migrate.ts` 增加分支，见 §6.11）

### 6.0 归属模型：多归属 + 版本化（本模块的两个结构性决定）

**决定一：一篇文章可以归属多个主题。** 学术文章跨主题是常态（例：一篇「高校图书馆生成式 AI 素养」同时属于「信息素养教育」与「生成式 AI 应用」）。采用**多归属 + 每篇上限 + 主归属标记**，而不是单归属的二选一。

**决定二：主题集合版本化。** 只有**规则/模型变更**才需要全量重聚类；届时产生一个新的*主题集合版本*，旧版本整集归档保留，保证旧 URL 与旧分析不失效（§7.9）。

#### 计数口径（必须先明确，否则处处歧义）

| 字段 | 含义 |
|---|---|
| `linked_count` | 该主题下的**唯一文章数**（含跨主题文章）。**单主题内不重复计数**，就是簇内文章数 |
| `primary_count` | 其中**以该主题为主归属**的文章数 |
| `period_added_count` | 本周期内新增的**链接数**（用于列表 `+N` 角标） |

> **注意**：一篇文章会同时出现在多个主题里，因此**所有主题的 `linked_count` 之和会大于全库文章数 817**。这是多归属的预期结果，不是 bug。但**单个主题内部不会重复计数**。

### 6.1 cluster_topic_sets（主题集合版本）

```sql
CREATE TABLE IF NOT EXISTS cluster_topic_sets (
  version INTEGER PRIMARY KEY,          -- 1,2,3…（应用层取 max+1）
  status TEXT NOT NULL DEFAULT 'active'
    CHECK(status IN ('active','archived')),
  trigger_reason TEXT,                  -- 见 §7.9 触发条件
  embedding_model TEXT,                 -- 快照：用于自动检测"模型换了要重建"
  embedding_dim INTEGER,
  facet_contract_version TEXT,          -- 切面契约版本（如 'v1'）
  init_threshold REAL,                  -- 冷启动阈值快照：检测"阈值大改要重建"
  note TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  archived_at TEXT
);

-- 任一时刻只允许一个 active 版本
CREATE UNIQUE INDEX IF NOT EXISTS idx_cts_single_active
  ON cluster_topic_sets(status) WHERE status = 'active';
```

> 该表同时充当**重建触发器**：把 `embedding_model` / `embedding_dim` / `facet_contract_version` / `init_threshold` 快照落库，流水线启动时与当前配置比对，不一致即告警并提示执行重建（§7.9）。

### 6.2 cluster_topics（主题）

```sql
CREATE TABLE IF NOT EXISTS cluster_topics (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  set_version INTEGER NOT NULL,       -- 所属主题集合版本
  slug TEXT NOT NULL,                 -- 形如 v1-t-003-a1b2c3；不可变、永不复用
  name TEXT NOT NULL,                 -- LLM 生成的主题名称
  keywords TEXT,                      -- JSON 数组，3~5 个核心词
  status TEXT NOT NULL DEFAULT 'NEW'
    CHECK(status IN ('NEW','ACTIVE','DORMANT','ARCHIVED')),
  centroid BLOB,                      -- float32[1024]，主题语义中心
  centroid_dim INTEGER,
  linked_count INTEGER NOT NULL DEFAULT 0,   -- 主题内唯一文章数
  primary_count INTEGER NOT NULL DEFAULT 0,  -- 主归属文章数
  period_added_count INTEGER NOT NULL DEFAULT 0,
  first_event_date TEXT,
  last_event_date TEXT,
  is_dirty INTEGER NOT NULL DEFAULT 1,
  last_analyzed_at TEXT,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  UNIQUE(user_id, set_version, slug)
);

CREATE INDEX IF NOT EXISTS idx_cluster_topics_set ON cluster_topics(set_version, status);
CREATE INDEX IF NOT EXISTS idx_cluster_topics_status ON cluster_topics(status);
CREATE INDEX IF NOT EXISTS idx_cluster_topics_dirty ON cluster_topics(is_dirty);
CREATE INDEX IF NOT EXISTS idx_cluster_topics_sort ON cluster_topics(set_version, period_added_count DESC, last_analyzed_at DESC);
```

| 字段 | 说明 |
|---|---|
| `slug` | 含版本前缀，因此跨版本天然不碰撞；永不复用；主题消失时置 `ARCHIVED` 而非删除 |
| `centroid` | 由**全部链接成员**的向量求均值再归一化（多归属下同一篇文章可计入多个主题，语义上成立） |
| `status` | `NEW` 新孵化 / `ACTIVE` 活跃 / `DORMANT` 长期无新增 / `ARCHIVED` 归档 |
| `is_dirty` | 脏标记；仅置位的主题进入步骤 6 的多维分析 |

### 6.3 article_cluster_facets（单篇切面 + 向量）

```sql
CREATE TABLE IF NOT EXISTS article_cluster_facets (
  article_id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL,
  facet_json TEXT NOT NULL,           -- 见 §7.1 切面契约
  facet_text TEXT NOT NULL,           -- 用于 embedding 的拼接文本（保留以便复算）
  facet_contract_version TEXT NOT NULL DEFAULT 'v1',
  embedding BLOB NOT NULL,            -- float32[1024]，小端
  embedding_model TEXT,
  embedding_dim INTEGER NOT NULL,
  event_date TEXT,                    -- 统一事件时间（见 §7.3）
  date_precision TEXT
    CHECK(date_precision IN ('day','year','ingest')),
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (article_id) REFERENCES articles(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_acf_user ON article_cluster_facets(user_id);
CREATE INDEX IF NOT EXISTS idx_acf_event_date ON article_cluster_facets(event_date);
```

> **本表不再存放归属**。归属移至 §6.4 的链接表；游离池判定为「该文章在 active 版本下无任何链接」，通过 `LEFT JOIN ... IS NULL` 得到（本表仅数百行，索引足够）。

### 6.4 article_topic_links（文章 ↔ 主题，多归属）

```sql
CREATE TABLE IF NOT EXISTS article_topic_links (
  article_id INTEGER NOT NULL,
  topic_id INTEGER NOT NULL,
  set_version INTEGER NOT NULL,       -- 冗余自 cluster_topics，用于按版本过滤
  similarity REAL NOT NULL,           -- 归入时与主题质心的余弦相似度
  is_primary INTEGER NOT NULL DEFAULT 0,   -- 主归属（每篇每版本恰好 1 条）
  link_rank INTEGER NOT NULL DEFAULT 1,    -- 按相似度排序，1 = 最高
  assign_method TEXT NOT NULL
    CHECK(assign_method IN ('init','centroid','incubation','reclaim')),
  assigned_at TEXT,
  PRIMARY KEY (article_id, topic_id),
  FOREIGN KEY (article_id) REFERENCES articles(id) ON DELETE CASCADE,
  FOREIGN KEY (topic_id) REFERENCES cluster_topics(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_atl_topic ON article_topic_links(topic_id, is_primary);
CREATE INDEX IF NOT EXISTS idx_atl_article ON article_topic_links(article_id);
CREATE INDEX IF NOT EXISTS idx_atl_set ON article_topic_links(set_version);

-- 每篇文章在每个版本下恰好一个主归属
CREATE UNIQUE INDEX IF NOT EXISTS idx_atl_one_primary
  ON article_topic_links(article_id, set_version) WHERE is_primary = 1;
```

| 约束 | 说明 |
|---|---|
| 每篇上限 | `CLUSTER_MAX_TOPICS_PER_ARTICLE`（默认 **2**，可调到 3） |
| 主归属 | `is_primary = 1` 取该文相似度最高的链接；由上面的 partial unique index 强约束 |
| 超限处理 | 已达上限时，**仅当**新相似度 > 该文现有最低链接相似度，才替换（删除被淘汰链接并重排 `link_rank` / 主归属） |
| `set_version` 冗余 | 取自 `cluster_topics.set_version`，该值写入后不可变，因此不会产生漂移；用于避免每次都 join 过滤版本 |

> **为什么值得冗余 + 加唯一索引**：多归属的真正成本在「计数口径」和「主归属唯一性」。把这两件事在库里强制住，应用层就不会出现「一篇文章两个主归属」或「列表数字对不上」的隐蔽 bug。

### 6.5 cluster_topic_remap（跨版本重定向）

重建主题集合时，用质心匹配为每个旧主题找最相似的新主题，用于**旧 URL 不失效**（访问已归档主题时提示并给出跳转目标）。

```sql
CREATE TABLE IF NOT EXISTS cluster_topic_remap (
  old_topic_id INTEGER NOT NULL,
  new_topic_id INTEGER NOT NULL,
  similarity REAL NOT NULL,
  from_version INTEGER NOT NULL,
  to_version INTEGER NOT NULL,
  created_at TEXT DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (old_topic_id, new_topic_id),
  FOREIGN KEY (old_topic_id) REFERENCES cluster_topics(id) ON DELETE CASCADE,
  FOREIGN KEY (new_topic_id) REFERENCES cluster_topics(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_ctr_old ON cluster_topic_remap(old_topic_id);
```

> 旧主题与新主题的 `slug` **不做迁移**（保持身份不可变、可审计）；重定向由本表驱动，而不是改写旧 `slug`。

### 6.6 topic_threads（簇内研究脉络）

```sql
CREATE TABLE IF NOT EXISTS topic_threads (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  topic_id INTEGER NOT NULL,
  angle_key TEXT NOT NULL,            -- 规则生成的角度稳定键（避免 LLM 改名导致漂移）
  angle_label TEXT,                   -- LLM 生成的角度名称
  article_count INTEGER NOT NULL DEFAULT 0,
  period_start TEXT,
  period_end TEXT,
  status TEXT NOT NULL DEFAULT 'ACTIVE'
    CHECK(status IN ('ACTIVE','DORMANT')),
```

## 7. 核心算法

### 7.0 模型与算法的边界（先说清楚，避免误读）

本模块**不是「零模型」**，也**不用任何专用小模型**。准确边界如下：

| 环节 | 实现 | 模型 | 说明 |
|---|---|---|---|
| 切面抽取 | LLM | ✅ 复用 | `getUserLLMProvider(userId, 'cluster_facet')` |
| 向量化 | embedding 接口 | ✅ 复用 | `getEmbedding()` / `getEmbeddingsBatch()`，现有 `BAAI/bge-m3`（1024） |
| 聚类（质心路由 / 阈值平均连接凝聚 / 游离池孵化） | **纯 TS** | ❌ | 零模型调用 |
| 簇内脉络（角度分群 / 时间串链） | **纯 TS** | ❌ | 零模型调用 |
| 周期指标（新增数 / 质心漂移 / 方法熵） | **纯 TS** | ❌ | 零模型调用 |
| 方法×对象对比矩阵 | **纯 TS** | ❌ | 零模型调用 |
| 主题命名 / 多维分析叙述 | LLM | ✅ 复用 | `getUserLLMProvider(userId, 'cluster_analysis')` |

**为什么不用专用小模型做「主题识别」**：

1. **与需求目标冲突**：任何分类器（含 zero-shot）都需预先给定候选标签集，而本模块的核心是「新主题自动涌现」。分类器从架构上就无法孵化新主题——必须用**无监督聚类**，而它天然是几何计算（相似度 + 簇间凝聚度），不需要模型。

> 注：封闭词表（§7.1）只约束**方法/对象矩阵的两条轴**，不影响主题发现——主题仍由向量上的无监督聚类自由涌现。
2. **会破坏向量空间一致性**：语义搜索已用 `bge-m3` 建库；聚类再用另一模型，等于维护两套不可比的向量空间（见 §8.1.3）。
3. **收益不成立**：817 篇量级下聚类计算是毫秒级，且**不耗 token**；瓶颈在 embedding 与切面质量，不在聚类算法。

> **推论**：模块质量几乎完全取决于**切面质量与向量对齐**，而非聚类算法选型。这是 §14.3 把「切面抽检 + 阈值校准」设为 P0 前置门禁的原因（垃圾进 → 垃圾出）。

### 7.1 切面抽取（LLM，每篇 1 次）

对 `ai_summary` 非空、且 `article_cluster_facets` 无记录的文章，调用 LLM 抽取结构化切面。

**输入**：`title` + `ai_summary`（截断至约 4000 字符）。
**输出契约**（强 JSON）：

```json
{
  "research_question": "……（≤120 字）",
  "method": "……（≤40 字，**只能取自方法词表**，多个用 + 连接）",
  "study_object": "……（≤40 字，**格式为「通用类别（具体样本）」**）",
  "core_finding": "……（≤160 字）",
  "limitation": "……（≤120 字，可为空字符串）",
  "angle_hint": "……（≤20 字，作者视角的可选线索）",
  "evidence_quotes": ["原文片段1", "原文片段2"]
}
```

**封闭词表（v2 起）**：`method` 与 `study_object` 的**类别部分**受词表约束，定义在 `src/topic-cluster/domain/vocab.ts`（`FACET_METHODS` / `FACET_OBJECTS`），并通过 `{{METHOD_VOCAB}}` / `{{OBJECT_VOCAB}}` 注入提示词——**代码与提示词同源，不维护第二份清单**。

为什么必须是类别而不是描述：自由文本下模型会写整句描述（实测首轮：对象键 52 个 / 提及 52 次，零重复），而方法×对象矩阵与空缺格推导要求**同一概念只对应一个键**。规范写法示例：

```
method:       文献研究 + 案例研究          ← 从词表选取（「文献综述」「文献分析」都归入「文献研究」）
study_object: 高校学生（38 所高校 213 名大学生）  ← 括号外是类别（词表内），括号内是个案细节
```

**读取时归一**：`normalizeMethodKeys` / `normalizeObjectKeys` 在**读取时**把历史切面映射到规范键（而非改写落库内容）——因此调整词表/别名**不需要重抽 817 篇**，只影响矩阵与熵的取值；词表外表述不产生键（原文照常展示），并由 `listOffVocabularyTerms` 批量告警，作为词表需要扩充的信号。

**校验规则**：

- 必填字段非空、长度上限达标；
- 拒绝占位符：`待编辑|待补充|TBD|TODO|placeholder|unknown|无|不适用`；
- `method` / `study_object` 必须是**可比较的规范词**（不得整句照抄研究问题）——由词表注入 + 读取时归一双重约束；
- `evidence_quotes` 至少 1 条，用于人工抽查切面是否忠于原文。

**`facet_text`**（embedding 输入）固定拼接：

```
QUESTION: {research_question}
METHOD: {method}
OBJECT: {study_object}
FINDING: {core_finding}
```

**失败处理**：单篇失败不阻断整批，记录到日志并在下次运行重试；不写占位切面。

### 7.2 冷启动（一次性）

1. 批量抽取全部历史全文总结的切面（817 篇，可并发受限批处理）。
2. 为全部切面生成 embedding（`getEmbeddingsBatch`，复用现有 embedding 配置，dim=1024）。
3. 创建**主题集合版本 1**：`cluster_topic_sets(version=1, status='active', trigger_reason='init')`，并把 `embedding_model` / `embedding_dim` / `facet_contract_version` / `init_threshold` 的**当前值作为快照写入**（用于后续自动检测「参数变了要重建」）。
4. 全量聚类（**纯 TS，无 UMAP/HDBSCAN**）：
   - 归一化全部向量；
   - 阈值平均连接凝聚（UPGMA）：每轮合并「两簇成员间**平均相似度**最高且 ≥ `θ_init`」的一对簇；
     * 不可用单链：单链判据是「两簇间最近的一对」，一条桥接对即可把不相干的簇并起来，产出「阈值 0.65、簇内最小两两 0.47」这种不可信主题；
     * 平均相似度用 Lance–Williams 更新式增量维护，避免每轮重扫成员对（O(n²) 内存、O(n³) 量级时间，817 篇数秒）；
     * `θ_init` 为**簇间平均相似度**，尺度恒低于单链判据，必须与连接方式成对校准（初始 0.65，待实测校准）；
   - 丢弃小于 `minClusterSize`（初始 3）的分量 → 归入游离池；
   - 对每个簇：`slug` = `v1-t-{seq}-{hash8}`；质心 = 成员向量均值再归一化；调用 LLM 生成 `name` / `keywords`。
5. 为每个簇的成员写链接：`article_topic_links(article_id, topic_id, set_version=1, similarity, is_primary=1, link_rank=1, assign_method='init')`，并刷新 `linked_count` / `primary_count`。
6. 剩余簇进入步骤 4~6 生成脉络与多维分析。
7. **封存全量脚本**：此后仅由增量流程接管。

> 冷启动脚本独立为 `scripts/cluster-init.ts`，**不放入调度器**，人工执行一次；且**只能创建 version 1**。若已存在 active 版本，重复执行必须改走 §7.9 的重建流程，不得就地覆盖。

### 7.3 增量归属路由（规则，每日）

```
对每篇未归属的新切面 f（在 active 版本下无任何链接）：
  sims = { t: cos(f.embedding, t.centroid) | t ∈ active 版本的 ACTIVE/NEW 主题 }
  hits = [(t, s) for (t, s) in sims if s >= θ_route]        # θ_route 初始 0.78
  hits = sorted(hits, by=s desc)[: CLUSTER_MAX_TOPICS_PER_ARTICLE]   # 默认 2

  if hits 为空:
      保持无链接 → 进入游离观察池
  else:
      for (t, s) in hits:
          if 该文在 active 版本下的链接数已达上限:
              # 仅当新链接比现有最差链接更相关时才替换
              if s > min(现有链接相似度): 删除最差链接；否则跳过该 t
          插入 article_topic_links(a, t, set_version, s, assign_method='centroid')
      重排：is_primary 给相似度最高者；link_rank 重排 1..N
      for 每个受影响主题 t:
          重算质心（= t 全部链接成员向量均值归一化）
          linked_count = 链接数；primary_count = 主归属数
          period_added_count += 本周期新增链接数；is_dirty = 1
          首/末 event_date 按需更新
```

**质心重算说明（多归属下的关键差异）**：不能再用「滑动平均增删」——一篇文章可能同时属于多个主题，且链接可能被上限机制淘汰，增减会失准。统一采用**从该主题当前全部链接成员重新求均值**：成员仅几十个，成本可忽略，且避免滑动平均的误差累积。

**统一事件时间（event_date）** 的计算与精度标记：

| 来源数据 | event_date | date_precision |
|---|---|---|
| `published_at` 非空 | 直接取用 | `day` |
| 仅 `published_year` | `{year}-06-15`（年中值） | `year` |
| 都没有 | `created_at` | `ingest` |

> 精度标记用于：① 跨精度不画承接箭头；② 趋势图对 `year`/`ingest` 数据加视觉区分。

**主题状态维护**：连续 `dormantDays`（默认 60）天无新增 → `DORMANT`；重新有新增 → `ACTIVE`。

### 7.4 游离池孵化（规则 + LLM 命名，每日）

```
pool = 在 active 版本下无任何链接的文章
       (article_cluster_facets LEFT JOIN article_topic_links ... WHERE link IS NULL)
if count(pool) < clusterMinPoolSize (初始 6):    # 需求原为 15，按实测下调
    return
对 pool 向量做阈值平均连接凝聚（θ_incubate = `CLUSTER_INIT_THRESHOLD`，与冷启动同一判据与尺度）
对每个 size >= minClusterSize (初始 3) 的分量:
    新建 cluster_topics（set_version=active, status='NEW', is_dirty=1）
    slug = v{ver}-t-{seq}-{hash8}；centroid = 分量均值归一化
    LLM 生成 name / keywords（输入：成员标题 + research_question + core_finding）
    为成员写链接（assign_method='incubation', is_primary=1）
    → 紧接着执行【定向回捞】（§7.4.1）
其余仍留在游离池
```

> **参数说明**：需求文档的 `pool ≥ 15` / `min_cluster_size = 4` 是按「每天有大量新文章」假设设定的。实测全文总结日增 1~4 篇，沿用原值会导致主题数周内无法孵化。本设计下调为 `≥6` / `≥3`，并**必须在实测中校准**（见 §14.3）。

#### 7.4.1 定向回捞（新主题的必修步骤）

**为什么必须做**：新主题只从游离池取文章，而游离池**只包含从未命中任何主题的文章**。那些**已被（错误地）路由到老主题**的文章根本没有机会加入新主题 → **新主题先天不全**。这是「不做全量重聚类」必然带来的副作用，必须用定向回捞补偿。

```
新主题 T 孵化后：
  for a in 全部已有切面的文章（含已归属的）:
      s = cos(a.embedding, T.centroid)
      if s >= θ_reclaim（初始 0.80，应 >= θ_route）:
          if a 链接数 < 上限: 追加 link(a, T, s, set_version, method='reclaim')
          else if s > a 现有最低链接相似度: 替换
  重排受影响文章的主归属与 link_rank
  重算 T 的质心 / linked_count / primary_count
  受影响的老主题：计数变化 + is_dirty = 1（触发重算分析）
```

**成本与边界**：O(817 × 1) 纯向量运算，**毫秒级**，**零 LLM 调用**；且因为不移动老主题的既有链接，**不会破坏老主题的质心**。

> 这里体现了选多归属的一个实质收益：回捞是**纯追加**。若为单归属，回捞必须「从老主题移走 + 重算老主题质心」，且会连带抖动老主题的所有分析。

### 7.5 簇内研究脉络（本模块核心，规则为主）

对每个主题执行（规模 27~40 篇，O(n²) 毫秒级）：

**第一步：角度分群（angles）**

```
按 (event_date, precision, article_id) 升序排列簇内文章
贪心 leader 聚类（对 facet 向量）:
   对每篇 a:
       找与 a 相似度 >= θ_angle (初始 0.82) 的已有角度中心，取最高者
       命中 → 加入该角度，并按成员数加权更新角度中心
       未命中 → 新建角度（以 a 为中心）
后处理:
   角度数上限 K (初始 6)；超出时按成员数合并最相近的角度
   成员数 < 2 的角度 → 并入最相近角度；若无 → 标记为 singleton（归入"零散研究"）
角度 angle_key = sha1(角度内 top 3 高频 method/object 词) 的前 12 位   # 稳定键
```

**第二步：时间内串链（threads）**

在每个角度内，按时间升序贪心链化：

```
chains = []                       # 每条链维护链尾 tail
对角度内每篇 a（按时间升序）:
    candidates = [c for c in chains
                  if sim(a.embedding, c.tail.embedding) >= θ_chain (初始 0.78)
                  and (shared_object(a, c.tail) or sim >= θ_strong (初始 0.88))]
   if candidates 为空:
       开新链，a.relation = 'origin'
   else:
       c = argmax 相似度
       接链，seq = c.length
       a.relation = 'continue' if (shared_object and shared_method)
                  else 'shift'
       若链尾与 a 的 event_date 精度不同 → 不画承接箭头（前端标记为"跨精度"）
```

**第三步：链条筛选**

- 链长 ≥ 3 → 作为正式脉络写入 `topic_threads`；
- 链长 < 3 → 归入该角度的"零散研究"，不生成脉络叙述（避免把巧合当成演进）。

**第四步：趋势标注（规则）**

```
前半段 = 时间中位数以前；后半段 = 其后
ratio = 后半段篇数 / max(前半段篇数, 1)
trend = 'up' if ratio >= 1.3 else 'down' if ratio <= 0.7 else 'flat'
样本 < minTrendSamples (初始 6) → trend = NULL（前端显示"样本不足"）
```

**第五步：LLM 命名与叙述（每主题 1 次，与 §7.7 同批）**

输入 = **已排好序、已成链**的结构化清单（角度 + 链条 + 每篇的切面摘要 + 指标），输出角度名称与每条脉络的一句话叙述，**每条叙述必须携带 `article_ids`**。

### 7.6 周期指标（规则）

按主题按月写入 `topic_metrics_period`：新增数、累计数、活跃角度数、平均归入相似度、质心位移（`1 - cos(prev_centroid, curr_centroid)`）、方法熵、对象熵。

### 7.7 多维分析合成（脏标记，仅 `is_dirty = 1` 的主题）

**输入组装**（只传切面，不传全文总结，控制 token）：

```json
{
  "task": "为给定主题生成多维分析。只能使用输入中给出的文章与其 field；不得引入外部知识。",
  "topic": { "name": "...", "keywords": [...], "linked_count": 32 },
  "angles": [{ "angle_key": "...", "articles": [{ "id": 123, "question": "...", "method": "...", "object": "...", "finding": "..." }] }],
  "chains":  [{ "angle_key": "...", "seq": [{ "id": 123, "relation": "continue" }] }],
  "metrics": [{ "period": "2026-05", "added": 4, "method_entropy": 0.42 }],
  "allowed_article_ids": [123, 124, ...]
}
```

**输出契约**（强 JSON，全部字段必填）：

```json
{
  "overview": "200 字以内的主题概述",
  "angles": [{ "angle_key": "...", "label": "...", "description": "...", "article_ids": [..] }],
  "threads": [{ "angle_key": "...", "narrative": "该脉络的问题→方法→发现演进", "article_ids": [..], "refute_notes": [] }],
  "trend_summary": "焦点转移的一句话描述，样本不足时写空字符串",
  "history_stages": [{ "stage_label": "...", "period": "YYYY-MM~YYYY-MM", "focus": "...", "article_ids": [..] }],
  "consensus": [{ "statement": "...", "article_ids": [..] }],
  "controversies": [{ "statement": "...", "article_ids": [..] }],
  "gaps": [{ "statement": "...", "basis": "覆盖缺口|邻近空白|时效缺口", "article_ids": [..] }]
}
```

**校验规则（不通过即 `status='failed'`）**：

1. schema 全字段校验 + 长度上限；
2. 占位符/空话检测：`待编辑|TBD|TODO|暂无|其他|unknown`；
3. **引用白名单**：所有 `article_ids` 必须是 `allowed_article_ids` 的子集，否则拒收；
4. `gaps[].basis` 必须落在枚举内，`basis = '覆盖缺口'` 时须能对应 matrix 的真实空格（服务端二次校验）；
5. 计算 `input_hash = sha256(prompt)` 落库，保证可复现与审计。

**落库后**：`is_dirty = 0`，`last_analyzed_at = now`。

> `comparison_matrix`（方法 × 研究对象）**不放进 LLM 输出**，由规则从切面聚合后存入 `matrix_json`（零 token，可筛选）。

### 7.8 研究空白的三个规则来源

为让「空白」不是空话，LLM 的输入必须包含三类**已算出的**空格：

| 类型 | 规则算法 |
|---|---|
| 覆盖缺口 | 构造 `method × study_object` 计数矩阵，取为 0 且两侧边际非零的格子 |
| 邻近空白 | 主题间质心相似度 ≥ `θ_adjacent`（初始 0.72）但**零文章重叠方法**的主题对 |
| 时效缺口 | 主题或某角度连续 ≥ `stalePeriods`（默认 3）个月无新增 |

LLM 只能从这些空格 + 各篇 `limitation` 中归纳 `gaps`，并必须回链文章。

### 7.9 主题集合版本化与重建

**日常不重建。** 只有在下列任一条件成立时，才执行全量重聚类并产生新版本：

| 触发条件 | 判定方式 |
|---|---|
| 阈值大改 | `init_threshold` 变化超过 ±0.03 |
| 切面契约变更 | `facet_contract_version` 变化 |
| embedding 模型或维度变更 | `embedding_model` / `embedding_dim` 变化 |
| 人工显式触发 | 执行 `scripts/cluster-rebuild.ts` |

**自动检测，但不自动重建**：流水线启动时把当前配置与 active 版本的快照比对；不一致则**告警并提示需要重建**。重建是重操作（全量聚类 + 全部主题重算分析），必须人工确认后执行。

**重建流程**（`scripts/cluster-rebuild.ts`）：

1. `version = max(version) + 1`；新版本 `status='active'` 并写入新的配置快照；旧版本置 `status='archived'`（partial unique index 保证任一时刻仅一个 active）。
2. 用**同一套切面与向量**重跑全量聚类（切面不重抽，除非 `facet_contract_version` 变了）。
3. 写入新版本的 `cluster_topics`（`slug` 带新版本前缀）与 `article_topic_links`（`set_version = 新版本`）。
   **旧版本的 topics 与 links 一律保留**，使已归档主题仍能完整渲染。
4. 为每个归档主题计算 `cluster_topic_remap`（质心最相似的新主题，`similarity` 落库）。
5. 重算指标与脉络，重跑多维分析（**仅新版本**）。

**查询约定（强制）**：所有面向用户的查询都必须以 `set_version = (active 版本)` 过滤。漏掉这一条，旧版本的主题就会混进列表。这是版本化最容易被忽略的代价，必须写进 Code Review 检查项。

**旧 URL 行为**：`/clusters/:id` 命中 `ARCHIVED` 主题时，页面提示「该主题已归档」并用 `cluster_topic_remap` 给出跳转目标；**不改写旧 `slug`**（身份不可变、可审计）。

#### 8.1.1 复用结论（已核实，不需改任何前端）

| 能力 | 现有入口 | 需要新增配置吗 |
|---|---|---|
| Embedding | `getEmbedding()` / `getEmbeddingsBatch()` → `getActiveConfigByType(userId,'embedding')` | 不需。直接复用现有 `BAAI/bge-m3`（1024） |
| LLM | `getUserLLMProvider(userId, taskType)` → 优先级「精确 `task_type` > `task_type IS NULL` 兜底」（`llm-configs.ts:671-700`） | 可选。不配也走兜底配置；配了则可为聚类单独指定模型 |
| 提示词 | `resolveSystemPrompt(userId, type, vars)` + `system_prompts` 表 | 需新增 2 个类型（见上表） |

**`/settings` 页面为什么不用改**：`panel-llm.ejs` 的任务类型下拉（`modals.ejs:122` 的 `#llmTaskType` 带 `data-type-category="task_types"`）与系统提示词的类型下拉，都由 `settings.js:72/84` 从 **`GET /api/types`** 动态填充，而后者直接读 `config/types.yaml` 并只返回 `enabled: true` 的项。因此**只要把两个 task_type 写进 YAML，两个下拉框会自动出现新选项**。

**附赠能力**：因为支持精确 `task_type` 匹配，可以为两个步骤配不同模型——`cluster_facet`（量大：冷启动 817 次）用便宜快模型，`cluster_analysis`（量小：仅脏主题）用强模型。

#### 8.1.2 三个实施陷阱（必须遵守）

1. **三处必须同步改**：`config/types.yaml`、`src/api/system-prompts.ts` 的 `DEFAULT_PROMPT_CONFIG`、`src/config/system-prompt-variables.ts` 的 `PROMPT_VARIABLES`。因为 `variablesToJSON(type)` 对未注册类型返回 `{}` 且**不报错**——漏改 `PROMPT_VARIABLES` 会导致提示词能建但设置页「变量说明」为空，问题隐蔽。
2. **默认提示词不会自动创建**：`ensureDefaultSystemPrompts()` 只在 `POST /api/system-prompts/bootstrap`（页面的「初始化默认模板」按钮）时触发。若要免手动，建议**加一个迁移分支**，照抄 `043_split_daily_summary_prompts.sql` 的写法（遍历所有用户插入新类型提示词）。或接受让管理员点一次按钮。
3. **`task_type` 目前没有后端强校验**：`TASK_TYPES` 在 `src/config/system-prompt-variables.ts` 导出，但全仓无任何使用处——校验仅靠前端下拉。建议新增模块时补一次显式校验（拒绝未注册的 `task_type`），否则 YAML 漏改时错误配置会静默入库。

#### 8.1.3 跨模块耦合（重要）

Embedding 是**全局单配置**（`getActiveConfigByType(userId, 'embedding')` 只取一个），因此**语义搜索与主题聚类共用同一个 embedding 模型**：

> 更换 embedding 模型会**同时**改变语义搜索与主题聚类的向量空间。这正是 §7.9 把「`embedding_model` / `embedding_dim` 变更」列为**必须重建主题集合**触发条件的原因。

## 9. API 设计

读接口：`requireAuth`（guest / user / admin 均可）。写接口：`requireAdmin`。数据统一读 `effectiveUserId`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/cluster-topics` | 主题列表。参数 `q`（检索 name/keywords，SQL LIKE）、`status`、`sort`（`added`/`analyzed`/`size`）、`page`/`pageSize` |
| GET | `/api/cluster-topics/:id` | 主题详情：基本信息 + `analysis_json` + 角度/脉络清单 + 统计 |
| GET | `/api/cluster-topics/:id/matrix` | 方法 × 研究对象对比矩阵（规则聚合，服务端实时计算） |
| GET | `/api/cluster-topics/:id/articles` | 主题下文章分页（含切面摘要、event_date、date_precision） |
| GET | `/api/cluster-topics/:id/history` | 研究历史时间轴（按 event_date 排序 + 每篇贡献点） |
| POST | `/api/cluster-topics/:id/reanalyze` | 手动重算该主题多维分析（admin） |
| POST | `/api/cluster-jobs/run` | 手动触发一次完整流水线（admin） |
| GET | `/api/cluster-jobs/status` | 最近一次运行状态与统计（admin） |

**排序逻辑（主题列表默认）**：`period_added_count DESC, status='NEW' DESC, last_analyzed_at DESC` —— 保证「今日有新增」与「刚孵化」的主题排最前。

**性能**：全部为 SQLite 单表/小连接查询 + 已落库 JSON 读取，目标 P95 < 20ms（不含 `matrix` 与 `history` 的聚合，二者目标 < 80ms）。

## 13. 分期范围

### P0 —— 数据地基与「角度 / 历史」

**范围**：§6 全部表（含版本化与多归属链接表）+ 切面抽取 + 冷启动聚类（version 1）+ 每日多归属路由 + 游离池孵化 + **定向回捞** + 落库；页面 a / e / g / h + 列表页；API 中 `list` / `detail(基础)` / `matrix` / `articles` / `history`。

**验收标准**：
1. `pnpm run typecheck` 通过；
2. 冷启动脚本对 ≥95% 的全文总结产出切面，抽检 20 篇，`method`/`study_object` 可比较（同义不同写的比例 < 20%）；
3. 生成主题数落在 15~35 合理区间；随机抽 3 个主题人工检查，簇内不相关文章占比 < 15%；
4. 每日流水线可重复执行且幂等（重复跑不产生重复链接）；
5. 列表与详情接口 P95 < 20ms / < 80ms；
6. **多归属约束生效**：任意文章在 active 版本下主归属恰好 1 条、链接数 ≤ `CLUSTER_MAX_TOPICS_PER_ARTICLE`；构造「超限」与「相似度并列」两种场景均不违反；
7. **定向回捞可验证**：手工构造一个「游离池孵出新主题」场景，确认已归属文章被正确追加，且**老主题质心与既有链接未被改动**。

### P1 —— 「脉络 / 趋势 / 空白」

**范围**：角度分群 + 时间串链（§7.5）+ 周期指标（§7.6）+ 多维分析合成（§7.7）+ 页面 b / c / d / f + `reanalyze` API + **`scripts/cluster-rebuild.ts` 与 `cluster_topic_remap` 填充（§7.9）**。

**验收标准**：
1. 对 ≥10 篇的主题，能产出 ≥2 个角度、≥1 条长度 ≥3 的脉络；
2. 抽检 3 条脉络，人工判断「承接关系成立」的比例 ≥ 70%（低于此则调整 `θ_chain`）；
3. 所有 `gaps` 的 `basis` 能对应到真实的矩阵空格（服务端校验 100% 通过）；
4. 引用白名单校验 100% 生效：构造越界 `article_ids` 时分析被拒且标记 `failed`；
5. `< minTrendSamples` 的主题 100% 走降级，不输出趋势文本；
6. **版本化可验证**：人为改一次阈值触发重建后，新版本生效、旧版本主题/链接/分析仍可完整访问、旧 `set_version` 数据不出现在列表中、旧 URL 能通过 `cluster_topic_remap` 给出跳转目标。

### P2 —— 增强

**范围**：全局主题地图（2D 投影）、语义检索（复用 Chroma）、主题漂移告警。

**验收标准**：地图投影稳定且可复现；漂移告警只针对真正的异常（`linked_count` 突增、质心位移超阈值），不产生噪声通知。

### 13.4 自动化边界与预留扩展点

#### 13.4.1 本期边界：无任何人工干预

本模块**不提供任何人工干预入口**。聚类、孵化、路由、脉络、多维分析全部自动完成，页面上只有「查看 + 检索」。

> **易混淆点（必须区分）**：§14 中出现的「人工抽检 / 人工判定」是**实现者在开发期离线做的质量门禁**（在样本上评估切面质量、簇纯度、脉络成立率），**不是产品功能**，不进入运行时路径，也不出现在页面上。这与「产品内的人工干预」是两件事。

#### 13.4.2 为什么仍要预留

全自动的直接后果是：**一旦线上出现错分，唯一的纠错手段是重新跑聚类脚本**。因此在不让本期多写一行业务逻辑的前提下，把未来的扩展成本压到「一次 ALTER + 一处条件判断」。

| 预留点 | 本期即遵守的设计约束 | 未来扩展所需改动 |
|---|---|---|
| 归属唯一写入点 | 所有对 `article_topic_links` 的写入必须经过单一函数 `assignArticleToTopic()`（内部统一处理上限、主归属、计数刷新），禁止散落在**路由 / 孵化 / 回捞**三处 | 在该函数内加 `manual_override = 0` 判断 |
| 游离池定义收敛 | 游离池 = 「在 active 版本下无任何链接」，该判定集中在单一函数 `listPoolCandidates()` | 查询内追加 `NOT EXISTS(人工排除)` 条件 |
| 「待孵化」与「人工排除」的区分 | §7.4 已明确：无链接当前**仅**表示「待孵化」 | 新增 `manual_override` / `override_action` 列；因回捞会扫描**已归属**文章，排除条件必须同时加在**路由、孵化、回捞**三处 |
| 分析状态可容纳复核态 | `cluster_topic_analysis.status` 已是枚举（`ok` / `insufficient_data` / `failed`） | 增加 `needs_review` 等取值，无需改结构 |
| 主题身份稳定 | `slug` 不可变；主题消失时归档不删除 | 人工合并/拆分可直接复用 |
| 归属变更可审计 | 暂不建表 | 新增 append-only 归属事件表 |

#### 13.4.3 明确不做

本期**不新增** `manual_override` / `override_action` / `overridden_by` 等字段。理由：现在加「永远不会被写入」的列，会让 Kysely 类型、迁移与 `001_init.sql` 同步携带无用字段，增加后续维护者的困惑；而本项目补一次迁移（`sql/NNN_*.sql` + `migrate.ts` 一个分支）的成本很低。相比之下，**「归属写入收敛到单一函数 + 孵化查询集中在单一构造点」是零冗余、零成本的扩展口子**——后期加功能只需改一处 + 一次字段迁移。

当未来需要人工干预时，应作为一个独立需求处理，并覆盖 §13.4.2 表格中的全部改动点，其中必须包含：**质心重算**（从该主题当前全部链接成员重新求均值）、**`thread_articles` 幽灵节点清理（`seq` 重排）**、以及**在路由 / 孵化 / 回捞三处同步加上排除条件**。

## 14. 实施前置与校准

> **说明**：本节全部动作由实现者在**开发期离线**执行，属于质量门禁；**不是产品功能**，不进入运行时路径，也不面向用户（与 §13.4 的「产品人工干预」无关）。

### 14.1 实现顺序（不可颠倒）

1. 表 + Kysely 类型 + migrate.ts 分支；
2. 切面抽取 + **人工抽检**（前置门禁，未通过不得继续）；
3. 冷启动聚类 + 簇纯度评估；
4. 每日路由 + 孵化 + 幂等验证；
5. 角度分群 + 串链 + 脉络抽检；
6. 多维分析合成 + 校验；
7. API + 页面。

### 14.2 验证方式

- 类型：`pnpm run typecheck`；
- 脚本：`scripts/cluster-init.ts`（冷启动）、`scripts/cluster-validate.ts`（切面抽检 + 簇纯度 + 脉络抽检，输出人工可读报告）；
- 幂等：连续运行每日流水线两次，比对 `article_cluster_facets` / `thread_articles` 行数与内容不变。

### 14.3 阈值校准流程（必须执行）

1. 取 50~80 篇样本跑切面 → 人工判定 `method`/`study_object` 可用性；
2. 用样本网格搜索 `θ_init ∈ [0.74, 0.86]`，以「簇纯度（人工判定）最高」为准；
3. 在 2~3 个真实主题上网格搜索 `θ_angle` / `θ_chain`，以「脉络承接成立率最高」为准；
4. 固化到 `.env.example` 与 `src/config.ts` 默认值，并在本文档记录最终值。

## 15. 对现有功能的影响与隔离边界

### 15.1 总体结论

架构上**纯增量**：新增 9 张表，**不对任何既有表做 ALTER**，不改动过滤 / 翻译 / 向量化 / 总结 / 每日总结 / 洞察报告任何一条既有流程。但有 6 个共享文件接入点与 3 个真实跨模块影响（§15.3），必须预先知晓。

### 15.2 会被修改的既有文件（均为加行，不改逻辑）

| 文件 | 改动 | 可见影响 |
|---|---|---|
| `src/index.ts` | 注册 `initTopicClusterScheduler()` + shutdown | 启动日志多一行 |
| `src/views/layout.ejs` | 导航新增一项 | ⚠️ **所有页面顶栏都会变**（对 guest 也可见） |
| `config/types.yaml` | 新增 2 个 `task_types` | ⚠️ 设置页两个下拉框多 2 个选项（现有项不变） |
| `src/api/routes.ts` | 注册新路由 | 无 |
| `src/api/web.ts` | 新增页面路由 | 无 |
| `scripts/migrate.ts` | 新增 1 个 if 分支 | 无（其余分支顺序不动） |
| `src/db.ts` | 新增 9 个表类型 | 无（纯类型追加） |

### 15.3 三个真实的跨模块影响（重点）

| # | 影响 | 原因（已核实） | 对策 |
|---|---|---|---|
| I1 | **抢 LLM 速率配额** | `src/llm.ts` 的限流器是**全局单例**（`initGlobalRateLimiter`），过滤/翻译/总结/聚类**共用同一个 token 桶**；冷启动 817 次切面抽取可能挤占其他任务 | 冷启动离线执行；每日任务排在全文总结 cron（07:00）之后；并发受 `LLM_RATE_LIMIT_*` 约束 |
| I2 | **阻塞 Web 服务** | `better-sqlite3` 是**同步驱动**；若流水线在紧循环里逐行写库，会阻塞唯一的 Node 事件循环 → 页面卡顿 | 必须**批量事务写入**（一次数百行）；禁止逐行 `await` 写；大批量时分批让出事件循环 |
| I3 | **SQLite 写锁竞争** | WAL 模式仍为单写者；README 已记录多进程导致 `SQLITE_ERROR` 的历史问题 | 与抓取/总结错峰执行；写事务保持短小 |

### 15.4 必须避开的陷阱：Chroma collection 不能复用

`src/vector/chroma-client.ts` 的 `getCollection(userId)` **只返回用户设置里的那一个 collection**（默认 `articles`），并按 `${collection}:${metric}` 缓存。

> 若新模块直接调用它，就会**写进现有语义搜索的 collection**，污染搜索与 `article_related`。

若选择 Chroma 方案，必须**新增独立的 `getClusterCollection(userId)`**，使用固定名称（如 `cluster_facets`）且与用户设置解耦。当前设计选择 **SQLite BLOB**，从根本上避开此陷阱（§6.3）。

### 15.5 代码目录布局

项目已有子系统文件夹先例（`src/telegram/`、`src/wechat/`、`src/gmail/`、`src/vector/`），因此本模块采用「**一个主文件夹 + 5 个按约定落位的接入点**」：

```
src/topic-cluster/                      ← 新模块主体（业务逻辑全部集中于此）
├── domain/                             纯函数：cosine / 平均连接凝聚 / 分链 / 指标 / 词表（可单测）
├── repo.ts                             Kysely CRUD（含归属唯一写入点 assignArticleToTopic）
├── facet.ts                            切面抽取 + schema 校验 + 拒收
├── analysis.ts                         多维分析 + schema 校验
├── embed.ts                            切面向量化（自存 BLOB，不碰既有 collection）
├── pipeline.ts                         6 步编排
└── config.ts                           模块内阈值读取

src/topic-cluster-scheduler.ts          ← 约定位置（项目所有调度器均在顶层）
src/api/cluster-topics.ts               ← 约定位置（服务层在 src/api/）
src/api/routes/cluster-topics.routes.ts ← 约定位置（路由须在 routes/ 并在 routes.ts 注册）
src/views/clusters.ejs / cluster-detail.ejs
src/public/js/clusters.js
sql/045_add_topic_cluster.sql
scripts/cluster-init.ts / cluster-validate.ts / cluster-rebuild.ts
```

### 15.6 向量化的确切对象（避免误读）

**不是**对 `ai_summary` 全文向量化，也**不是**新建独立向量数据库实例。

| 项 | 结论 |
|---|---|
| 输入范围 | 有全文总结的 817 篇（§2.1） |
| 向量化的文本 | **切面文本 `facet_text`**（QUESTION / METHOD / OBJECT / FINDING 拼接），不是 `ai_summary` 原文 |
| 存哪儿 | **SQLite BLOB**（`float32[1024]`，4KB/行，817 行 ≈ 3.3MB）；不用独立向量库 |
| 为什么不用全文 | ① 问题/方法/对象/发现才是聚类判别特征，背景叙述是噪声；② 现有全文总结长度差 26~9811 字符，直接 embedding 会让长文主导距离；③ 规范化后的 `method`/`study_object` 才能支撑方法×对象矩阵与空白推导 |
