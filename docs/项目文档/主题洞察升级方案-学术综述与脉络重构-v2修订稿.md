## 1. 目标、边界与不变量

### 1.1 两类用户任务

| 任务 | 用户问题 | 系统必须提供 | 系统不应提供 |
|---|---|---|---|
| **阅读** | 这个主题在做什么？从哪读起？有哪些子域和分歧？ | 可回链的核心文献、子域划分、共识/争议、方法演化 | 无证据的“理论框架”套话、伪引用编号 |
| **选题** | 哪里还有空白？哪条线正在升温？ | 可检验的空白（矩阵空格/跨主题缺组合/时效停滞）、前沿探针、局限证据 | “该领域研究不足”这类无法证伪的结论 |

### 1.2 不变量（实现时不得违反）

1. **页面访问不触发 LLM**。所有综述在批处理中生成并落库；前端只读缓存。
2. **引用白名单**。任何 `article_id` 必须来自当前输入集合（跨主题空白例外，见 §4.3，且需单独标注来源）。
3. **不伪造学术关系**。系统没有引文数据，只能表述为“语义相邻 / 方法延续 / 对象延续”，不得写成“引用/继承/师承”。
4. **失败不写占位文本**。LLM 失败时保留上一次成功结果，`status='failed'`，下轮重试。
5. **每篇文献恰好一个结构角色**。不允许“既在主干又在卫星”或“无角色”。
6. **综述字段可回链**。没有 `basis_article_ids` 的论断不得进入共识、争议、范式综述与空白。

### 1.3 成功指标（验收用）

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 大主题（≥200 篇）非空子域率 | 100% | `angles.length >= 3` 且 `loose` 只含缺失切面成员 |
| 文献角色覆盖率 | 100% | 所有 `article_topic_links` 成员都有 `academic_role` |
| 分析输入预算 | ≤24,000 字符 | 打包函数返回值 + 单测 |
| 单阶段输出截断率 | 0 | 解析器记录 `finish_reason=length` 为失败并告警 |
| 论断回链率 | 100% | 每个 synthesis/paradigm/gap 条目 `basis_article_ids` 非空（或显式“证据不足”） |
| 新文献可见延迟 | ≤1 天 | 日派生任务时间戳 |

## 2. 第一优先：脉络召回（P0-4、P0-5）

### 2.1 当前失败链（代码级）

1. `groupAngles` 贪心 leader 聚类，超过 `maxAngleCount=6`（`config.ts:55`）后由 `mergeUntilLimit`（`chaining.ts:223`）反复合并最相似角度 → 每个桶 30~50 篇。
2. `buildSteps` 在桶内按 `eventDate` 排序，逐对算相似度，`continuity = 相似度 >= chainThreshold(0.78) 的相邻对占比`（`chaining.ts:143-181`）。
3. `buildThreads` 要求 `steps.length >= 3 && continuity >= 0.5`，否则整桶 `loose.push(...angle.members)`（`chaining.ts:183-205`）。
4. 于是 6 个角度可能全部被抹杀；`threadsJson` 为空，`allowedAngleKeys` 为空，LLM 无权返回角度；前端 `angles` 为空即隐藏整块。

**结论**：问题不在“6 太小”，而在“先强行压成 6 个大桶，再用一条严格的时间链去否决整个桶”。只把 6 改成 10，只是把 30~50 篇的桶变成 20~30 篇的桶，连续性仍然过不了 0.78。

### 2.2 子议题划分：平均连接 + 目标簇数，而不是只升 K

**复用**：`domain/clustering.ts` 已有平均连接凝聚 `cohesionClusters`（`clustering.ts:70`），生产默认 `average`。它当前只按阈值停 merged，没有“目标簇数”参数，需要小幅扩展：

```ts
export interface CohesionOptions {
  minSize: number;
  linkage?: Linkage;
  /** 新增：切到该簇数即停止合并（护栏，不是唯一判据） */
  targetCount?: number;
  /** 新增：下一次合并的平均相似度低于此值时停止，避免为凑 K 强行合并异质簇 */
  cutSimilarityFloor?: number;
  onProgress?: (done: number, total: number) => void;
}
```

**算法**：

1. 对主题成员构建相似度矩阵（已有 `buildSimilarityMatrix`）。
2. 按平均连接做凝聚，记录每次合并的平均相似度。
3. 停止条件（三者先到先停）：
   - 当前簇数 `<= K_target`；
   - 下一次合并相似度 `< cutSimilarityFloor`（初始 0.78，与主题入门阈值一致）；
   - 只剩 1 簇。
4. 小于 `minSize` 的簇并入“平均相似度最高且共享至少 1 个方法或对象”的簇；仍无归属则标记为 `frontier`，不丢弃。`minSize = clamp(floor(N / K_target), 2, 4)`：N=243 时为 4，N=10 时为 3，避免“3 个簇 × 每簇至少 4 篇”在小主题上无解。
5. 每个簇的质心用成员向量重算（不是 leader 向量）。

**K_target 公式（护栏）**：

```
K_target = clamp(ceil(N / 18), 3, 10)
```

| N | K_target | 说明 |
|---|---|---|
| 10 | 3 | 小主题保底 3 个视角 |
| 60 | 4 | 中等主题 |
| 120 | 7 | |
| 243 | 10 | 上限 10，避免碎成不可读的 20+ 子域 |

> 与 v1.6 的 `sqrt(N/2)` 的差别：那条公式在 N=243 时直接顶到 10，但没有解决“桶内异质”的问题；v2 的目标簇数只是停止条件之一，真正的质量由平均连接与 `cutSimilarityFloor` 保证。

### 2.3 弹性承接：发散角度绝不整块删除

#### 2.3.1 判定

对每个角度（簇）：

1. 按 `eventDate` 升序（空日期排最后，再按 articleId 保证确定性）。
2. 计算相邻相似度与 `continuity`（沿用 `buildSteps`）。
3. 判定：
   - `linear`：`steps.length >= 3` **且** `continuity >= linearContinuityThreshold`（初始 0.5）。
   - `divergent`：其余所有角度。**仍然保留**，不再 `loose.push`。
4. `divergent` 角度内：
   - 取离质心最近的 3 篇 + 最新发表的 1 篇（去重后 3~4 篇）作为 `representatives`；
   - 其余成员保留在角度内，按 §2.5 分配 `satellite` / `frontier`；
   - 角度仍需 LLM 写 80~200 字 `narrative`，但提示词明确要求“这是发散子域，不要编造时间演进”。

#### 2.3.2 数据结构

```ts
export interface Thread {
  angleKey: string;
  patternType: 'linear' | 'divergent';
  steps: ChainStep[];
  representatives: number[]; // 仅 divergent 使用
}
```

`loose` 的语义收窄为：**只有缺失切面、无法参与任何计算的成员**。正常主题的 `loose` 应为空；若不为空，`derive` 日志必须告警（现有 `missingFacetArticleIds` 已具备）。

#### 2.3.3 阈值校准（必须做，不再拍脑袋）

上线前用离线脚本对现有 230 篇切面做统计：

- 每个角度的 `continuity` 分布（P10/P25/P50/P75/P90）；
- `linear` 在 0.4 / 0.5 / 0.6 三档下的角度数与平均链长；
- 目标：`linear` 角度占比 30%~60%，且平均链长 ≥3。

若 0.5 下 `linear` 占比 <20%，说明 `chainThreshold=0.78` 过严，应先调 `chainThreshold`（0.72~0.75），而不是继续降 `continuity`。校准结果写入 `docs` 并固化到 `CLUSTER_LIMITS`。

### 2.4 `angle_key`：稳定身份、唯一落库（P0-4）

**问题一：撞键**。`buildAngleKey` 只取成员 top3 方法 + top3 对象做 8 位哈希（`chaining.ts:296-308`）。角度扩到 10 后，多个簇共享同样的高频方法/对象签名非常常见；`replaceTopicThreads` 先 `delete` 再逐行纯 `INSERT`（`repo/threads.ts:39-53`），撞 `UNIQUE(topic_id, angle_key)` 会让整个事务抛错，derive 中断。

**问题二：漂移**。成员增删会改变 top3 签名，`angle_key` 变化后：
- `applyAngleNarratives` 按 key 回填失败；
- Changelog 无法对比“同一子域上次说了什么”；
- 前端锚点失效。

**v2 规则**：

1. **身份继承优先于重新哈希**。重建前读取旧 `topic_threads` + `thread_articles`，对新簇与旧线索做匹配：
   - 成员 Jaccard 相似度 `|A∩B| / |A∪B| >= 0.5`，或质心余弦 `>= 0.92` 且共享至少 1 个成员；
   - 取相似度最高的旧线索，**复用其 `angle_key` 与 `angle_label`**；
   - 每个旧 key 只能被复用一次（贪心按相似度降序分配）。
2. **新簇生成新 key**：仍用 top3 方法/对象签名，但追加冲突后缀：
   ```
   a-<hash8>        // 首次
   a-<hash8>-2      // 同批次第二个同签名簇
   a-<hash8>-3
   ```
   后缀按“成员数降序、最小 articleId 升序”确定性分配，保证同一输入多次运行结果一致。
3. **落库前内存去重**：`replaceTopicThreads` 入口断言 `new Set(rows.map(r => r.angleKey)).size === rows.length`；不满足直接抛错（fail-fast，不静默改 key）。
4. **upsert 兜底**：SQL 改为
   ```sql
   INSERT INTO topic_threads (...) VALUES (...)
   ON CONFLICT(topic_id, angle_key) DO UPDATE SET
     angle_label = excluded.angle_label,
     article_count = excluded.article_count,
     pattern_type = excluded.pattern_type,
     ...
   ```
   即使前两步有遗漏，也不会中断整轮。
5. **`inputHash` 纳入 `patternType` 与代表文献 ID**，否则结构变了但 hash 不变，分析会被错误跳过。

### 2.5 卫星、前沿与角色模型（P0-5）

#### 2.5.1 为什么 0.60 不能用

- 主题入门阈值是 `simThreshold=0.78`、`angleThreshold=0.82`（`.env.example:161,167`）。
- 把一个与子域质心只有 0.60 的文献称为“卫星”，等于把主题边缘以外的文献也吸进来；在 243 篇的大主题里，0.60 会吸走大量异质文献，卫星抽屉变成第二个垃圾桶。
- 反过来，0.60 对某些高度同质的子域又过严，导致本应挂载的案例掉进 `frontier`。

#### 2.5.2 相对分位判定

对每个角度 `k`：

1. 计算每个成员 `i` 与角度质心的余弦 `s_ik`。
2. 取该角度成员相似度的 `P30` 作为局部下限。
3. 判定：
   - `s_ik >= max(0.68, P30)` **且** 与角度多数成员共享至少 1 个方法或对象 → `satellite`；
   - 否则若 `s_ik < P20` 且携带“主题内出现次数 ≤2 的方法或对象” → `frontier`；
   - 其余 → 保持 `divergent`（发散子域成员）。
4. 全局护栏：
   - `satellite` 占主题成员比例 ≤30%；超出时按 `s_ik` 从低到高改判为 `divergent`；
   - `frontier` 最多 12 篇；超出时保留“方法/对象新异度”最高的 12 篇，其余回到 `divergent`。
5. `linear` 角度内不产生 `satellite`：当前 `buildSteps` 会为角度内每篇成员生成 step，因此它们全部是 `backbone`。若后续把“只保留高置信链”作为独立改动，未进链的同簇成员再按 §2.5.2 处理（本次不做）。

> 初始值 `0.68 / P30 / P20` 必须用同一批 230 篇数据校准；目标是卫星占比 10%~25%、frontier 占比 2%~8%。校准前不要写死到提示词里。

#### 2.5.3 角色优先级（解决 v1.6 的五级冲突）

结构角色**互斥且落库**，`landmark` 只是展示叠加层：

| 优先级 | `academic_role` | 判定 | 是否落库 |
|---|---|---|---|
| 1 | `backbone` | 属于 `linear` 角度的链上步骤 | 是 |
| 2 | `divergent` | 属于 `divergent` 角度且非卫星/前沿 | 是 |
| 3 | `satellite` | §2.5.2 判定 | 是 |
| 4 | `frontier` | §2.5.2 判定 | 是 |
| — | `landmark`（叠加） | 被 `synthesis` / `paradigm_reviews` / `gaps` 引用 | 否，查询时由 `basis_article_ids` 派生 |

这样：
- 每篇文献恰好一个结构角色；
- “核心基石”不会与“演进主干”互斥冲突；
- 不需要为用户不可见的优先级写复杂规则。

## 3. 第二优先：契约、预算与证据链（P0-1、P0-2、P0-3、P0-6）

### 3.1 输入打包：先定预算，再写 Prompt（P0-1）

**现状**：`buildThreadPayload`（`analysis-runner.ts:164`）把每个 `thread` 的**全部**成员输出为 5 个 facet 字段（research_question / method / study_object / core_finding / limitation），243 篇 ≈ 243 × 5 × 60~120 字 ≈ 70k~140k 字符。v1.6 的“4.8k~6.8k tokens”只估了输出，没有估输入。

**v2 新增模块** `src/topic-cluster/service/analysis-payload.ts`：

```ts
export const ANALYSIS_INPUT_CHAR_BUDGET = 24_000;

export interface PackedAnalysisInput {
  chars: number;
  truncated: string[];       // 记录裁剪了哪些层，写日志
  threadsJson: string;
  matrixSummary: string;
  statsText: string;
  evidenceByArticleId: Map<number, EvidencePack>;
}
```

**四层打包**（按优先级从高到低保留）：

| 层 | 内容 | 上限 | 超限裁剪 |
|---|---|---|---|
| L1 角度骨架 | 每个角度：key、label、pattern、memberCount、period、continuity；每角度最多 12 条步骤（id、year、relation、method、object、finding ≤40 字） | 10 × 12 × ~80 字 ≈ 9.6k 字符 | 每角度步骤降到 8 → 6，但**角度列表与 key 永不裁剪** |
| L2 代表文献 | `linear` 每角度 ≤10 篇；`divergent` 每角度 4 篇代表作 + 4 篇卫星；每篇 5 字段（finding/limitation 截断 120 字） | 40 × ~180 字 ≈ 7.2k 字符 | 每角度代表从 10 降到 6；核心 3 篇永不裁剪 |
| L3 矩阵摘要 | 已有格 ≤20 + 空缺 ≤10（`renderMatrixSummary` 当前 maxCells=25） | ≈ 1.8k 字符 | 格数 20→12，空缺 10→6 |
| L4 计量摘要 | 最近 12 个月：新增/累计/漂移/熵 | ≈ 1.5k 字符 | 12 → 6 个月 |
| L5 变更上下文 | 上次综述摘要（≤300 字）+ 新增文献列表（≤10 条） | ≈ 1k 字符 | 新增列表 10→5 |

**默认目标 24k 字符**，超限时按 L4 → L3 → L1 步骤 → L2 代表的顺序裁剪；**白名单 ID 集合不裁剪**（它不进入 Prompt 正文，只用于校验）。

> **实施注（I2/I3 自适应预算）**：生产预算不再硬编码 24k，而是由
> `CLUSTER_ANALYSIS_CONTEXT_TOKENS - CLUSTER_ANALYSIS_OUTPUT_TOKENS - 2k(Prompt 开销)`
> 换算为字符（按 1 token≈0.8 字保守估计）；128k/16k 默认约 87.7k 字符。
> 预算越大，每角度步骤与 L2 代表数按 sqrt 放大；超限时按实际超出比例逐轮收缩，
> 不再“一超限就砍到最小”。24k 仅作为单测/小模型的保底默认。

**为什么不是 40 篇一刀切**：`maxArticlesPerAnalysisInput=40` 是命名任务的采样上限，不适合综述；综述需要“每个角度都有代表”，而不是“全局前 40 篇”。v2 按角度配额采样，避免某个 47 篇的密集格独占输入。

### 3.2 输出预算：两阶段生成（P0-2）

**现状**：`synthesizeAnalysis` 单次 `maxTokens: 3000`（`llm/analysis.ts:82`）。新契约的中文字符下限估算：

| 部分 | 字符数 |
|---|---|
| synthesis 五维 | ~600 |
| consensus + controversies | ~240 |
| angles 10 × 200 | ~2,000 |
| paradigm_reviews 5 × 430 | ~2,150 |
| frontier_insights | ~150 |
| bibliometrics 四项 | ~400 |
| gaps 12 × 60 | ~720 |
| **合计** | **~6,260 字** |

中文 1 字 ≈ 1~1.5 token，加 JSON 结构后约 7k~9k tokens，3000 必然截断。

**v2 拆两阶段**：

| 阶段 | 产出 | `maxTokens` | 输入 |
|---|---|---|---|
| A | `synthesis`、`overview`、`angles[].narrative`（含 `pattern_type`） | `min(8192, 输出预算)` | L1 + L2（linear 代表）+ L4 |
| B | `paradigm_reviews`、`frontier_insights`、`bibliometrics`、`gaps`、`changelog.summary` | `CLUSTER_ANALYSIS_OUTPUT_TOKENS`（默认 16384） | L2（范式域代表）+ L3 + L4 + 阶段 A 的 `synthesis` 摘要 |

**失败隔离**（新增状态 `partial`，需同步扩展 `AnalysisStatus` 与 CHECK）：

1. 阶段 A 成功 → 立即 `upsertTopicAnalysis` 写入 `analysis_json`（含 `synthesis`、`angles`、`overview`），`status='partial'`；`is_dirty` 保持 1。
2. 阶段 B 成功 → 合并写入，`status='ok'`，`clearTopicDirty`。
3. 阶段 B 失败 → 保留阶段 A 内容，`status='partial'`，`error_message='phase_b: ...'`，`is_dirty` 保持 1；下一轮只重跑 B（`analysis_json.phase_b_status='failed'`）。
4. 阶段 A 失败 → 保留旧结果，`status='failed'`，下一轮重跑 A+B。
5. `pipeline/analyze.ts` 的计数增加 `partial`：既不清脏标记，也不计入 `failed`；日志单列，避免“部分成功”被误报为失败。

> 不能沿用 `status='ok'` 表示“阶段 A 已完成”：现有 `runPendingAnalyses` 在 `ok` 时会 `clearTopicDirty`（`pipeline/analyze.ts:52-56`），阶段 B 将永远不会重跑。

**为什么不是单次 8192**：单次调用一旦末尾截断，整份 JSON 报废，阶段 A 也丢；两阶段的成本增加约 15%（共享输入可缓存），但把“全有全无”变成“可局部重试”。

**验收**：解析器把 `finish_reason === 'length'` 当作显式失败，日志记录阶段与字符数，禁止静默 `JSON.parse` 失败后写空。

- 词表是 22 方法 × 22 对象，但矩阵只保留出现次数 ≥2 的高频项（`matrix.ts:53`）；实际维度随主题变化。
- 前端文案不要写“221 格”，改为“高频方法 × 高频对象（本主题 M × O）”。
- `MatrixCell.articleIds` 已存在，可直接用于抽样与前端钻取，无需新增结构。

### 4.2 范式域聚合（规则层，零 token）

**目标**：把“格子”聚成 3~5 个可读的范式域，而不是让 LLM 面对几十个格。

**算法**（`service/paradigm.ts` 新增）：

1. 对每个有文献的格 `(method, object)`，计算格内成员向量质心 `c_cell`。
2. 以格为节点，边权 = `cos(c_i, c_j)`；用平均连接凝聚（复用 `cohesionClusters` 的思路，节点是格而非文章）。
3. 停止条件：域数 3~5，或下一次合并 `< 0.80`。
4. 每个域的文献池 = 成员格的文章并集；按 §4.2.1 抽样。
5. 域名称、方法/对象列表由规则生成初稿，LLM 只写四段叙述，不重新分组。

#### 4.2.1 域内抽样配额

| 类型 | 数量 | 选取规则 |
|---|---|---|
| 核心基石 | 2~3 | 距域质心最近 |
| 创新发散 | 2~3 | 与已选集合最小相似度最大（贪心最大最小距离） |
| 前沿时效 | 1~2 | 最新发表 |
| **合计** | **≤7** | 其余文献只给 ID 列表，不进 Prompt |

**稀疏格处理**：`C=1~2` 的格不单独成域；仅当与邻近格共享同一对象或同一方法，且格质心 `cos >= 0.85` 时合并；否则在矩阵中标注“单篇特异视角”，不强行综述。

### 4.3 空白：从三类到四类，并真正用上 `adjacent`

**现状**：`findAdjacentTopics` 已计算邻近主题与共享方法/对象（`query.ts:463-527`），`adjacentTopicThreshold=0.72` 也已定义（`config.ts:80`），但全库无引用；`matrix.ts` 顶部注释写了 `adjacent_topic`，实现里没有。

**v2 定义**：

| `basis` | 证据 | 生成方式 |
|---|---|---|
| `matrix_hole` | 高频方法 × 高频对象从未交叉 | 规则直接给出，LLM 只写“为什么值得做” |
| `cross_topic_gap` | 主题 A 常用方法 M，邻近主题 B 常用对象 O，且 A 内无 M×O、B 内也无 M×O | 规则计算候选，LLM 写假设；证据 ID 可来自 A/B，标 `scope` |
| `staleness` | 某子域连续 `stalePeriods=3` 个月无新增 | 规则给出 |
| `limitation` | 多篇 `limitation` 字段指向同一未解问题 | 规则聚类 + LLM 归纳 |

**`cross_topic_gap` 计算**（`service/gap-builder.ts`）：

1. 取当前主题的邻近主题（现有 `findAdjacentTopics`，最多 5 个）。
2. 对每个邻近主题，读取其成员 facet 的方法/对象集合。
3. 候选 = `(A.methods × B.objects) ∪ (B.methods × A.objects)`，且该组合在 A、B 内均无文章。
4. 按 `min(methodCount, objectCount)` 排序，取前 5 条。
5. LLM 只负责把候选写成“可检验假设”，不得新增候选。

**提示词约束**：`cross_topic_gap` 的 `evidence_scope='adjacent'`，前端显示“跨主题证据”，不与本主题引用混排。

### 4.4 全量底册与“取消实时钻取”

- `TopicDetail` 新增 `allArticles: TopicArticleItem[]`，字段：id、title、url、year、role、patternType、method、object、researchQuestion、isPrimary、similarity。
- 243 篇一次性返回约 243 × 200 字 ≈ 50KB，可接受；前端分页 20/50，不做服务端分页（避免新增接口）。
- **删除 v1.6 的矩阵点击实时 LLM 钻取（模式 B）**：
  - 违反“页面访问不触发 LLM”；
  - 任务名在 v1.6 中同时出现 `matrix_cell_review` 与 `cluster_matrix_review`，路由参数也不一致（`/:id` vs `/:slugOrId`）；
  - 实时生成无法进入 Changelog 与白名单审计。
- 矩阵点击改为：展示该格文献列表 + 已有的范式域叙述（若该格属于某个域）+ 空白的规则解释。若未来确需实时生成，作为独立开关 `CLUSTER_MATRIX_REVIEW_ENABLED=false` 默认关闭，且必须先补任务类型与审计。

## 11. 一句话结论

v1.6 的产品方向（学术综述、子域脉络、范式交叉、全景底册）是对的；v2 不改变方向，只改变**先后与口径**：先把“每篇文献有角色、每个角度能落库”做扎实，再把“输入有预算、输出不截断、论断有证据”补上，最后才做范式域、底册与 UI。这样 243 篇大主题的升级才是可验证的，而不是把同一批空数据换一套更漂亮的壳。
