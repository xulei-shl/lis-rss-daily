# 我的每日模块：功能与逻辑分析

本文基于仓库里的实际代码，说明「我的每日」模块做什么、怎么运转。它是给维护者和二次开发者看的功能与逻辑说明，不是需求文档。需求口径见 [我的每日-JEV评分实现逻辑.md](../jev-docs/需求/我的每日-JEV评分实现逻辑.md)。

## 1. 这个模块做什么

「我的每日」给每个用户算出当天新增文章的相关性分数，再把分数落库、排序、展示。

它解决一个问题：用户订阅了很多来源，每天抓回大量文章，人工看不过来。模块用 JEV（TypeSafe 的相关性判断服务）给每篇文章打一个 0 到 1 的分，分高的排前面，分低的灰显，失败的单独标出。用户可以按日期回看，也可以让外部 agent 通过 API 取当天的精选。

分数不是关键词匹配，是一次模型推理的结果。模块把文章标题、摘要和用户关注的主题领域一起发给 JEV，JEV 返回「是否相关」和「相关到什么程度」，模块再把两者合成一个分。

## 3. 分数怎么来

### 3.1 选哪些文章

调度器按用户时区算出「当天」这个自然日，再换算成对应的 UTC 区间去查 `articles` 表。`created_at` 落在区间内（两端都闭）就算当天文章。这样凌晨抓的文章不会被拆到两天。

这里不按 `filter_status` 过滤。需求要 JEV 给当天所有新增文章打分，已经过关键词预过滤的文章也参与。

### 3.2 每篇文章配什么主题

每篇文章只带一个主题领域，除非解析不出。逻辑在 `resolveArticleTopics`：

1. 文章的 `source_origin` 指向某张源表（`rss_sources` / `journals` / `keyword_subscriptions` / `email_sources` / `web_sources`）。
2. 按来源类型批量反查这些表上的 `domain_id`。
3. 用 `getTopicDomainById(domainId, userId)` 做所有权校验，确认领域属于当前用户。
4. 校验通过就只把这一个领域和它的激活关键词交给 JEV。判断更聚焦，prompt 更小，领域归属也直接确定。
5. 校验不过（源没绑领域、领域已删、领域不属于该用户）就回退到用户全部激活领域。

绑定领域不做 `is_active` 过滤，它是源上显式做出的归档选择。关键词只取激活的。回退篇数在日志里用 `fallbackCount` 报告，大于 0 时另打一条 warn。

### 3.3 一次 JEV 调用问三件事

`buildJevRequest` 把文章和主题拼成 `state`，再问三类问题：

| 问题 key | 类型 | 作用 | 什么时候问 |
|---|---|---|---|
| `is_relevant` | `noul` | 二值判断，相关或不相关 | 始终问 |
| `relevance_level` | `score` | 0 到 4 五档相关程度 | 始终问 |
| `best_domain` | `choice` | 从多个领域里选最匹配的一个 | 只在回退到多领域时问 |

`noul` 给粗粒度的门控，`score` 给细粒度程度，`choice` 给领域归因。三者各自独立提问。

### 3.4 合成公式

```
relevanceScore = round(noul概率 × (score值 / 4) × 100) / 100
```

`noul` 概率在 0 到 1 之间，当门控。`score` 归一化到 0 到 1，当程度。两者相乘，被判不相关的文章即使 score 高也会被压到接近 0。结果保留两位小数。

`matched_domain` 的取法分两种。单领域提问（含来源绑定领域）直接取该领域名。多领域回退时取 `choice` 的答案，答案缺失就是 `null`，不会随便退回某个领域。

字段缺失有兜底。`is_relevant.noul` 或 `relevance_level.score` 不是数字时按 0 处理。这种情况 `failed` 仍是 `false`，会被当成真实的 0 分低相关，和「JEV 调用失败」是两回事。

### 3.5 失败占位

JEV 调用失败时（`scoreArticle` 的 catch 分支），返回 `relevanceScore = 0`、`matchedDomain = null`、`jevResponse = { error: message }`、`failed: true`。`latencyMs` 还是真实耗时。这个 0 分是占位，不代表真实相关性。

判定一次调用是否失败，统一用 `isJevResponseFailed`。它解析 `jev_response`，只要 `error` 字段是字符串就算失败。这个函数已导出，DB 里成功和失败的记录靠它区分。

## 4. 调度与并发

### 4.1 定时任务

cron 默认 `30 7 * * *`，每天 07:30 跑。可用 `MY_DAILY_SCHEDULE` 改。

任务遍历所有 `role='user'` 的用户，串行逐个评分。日期按各用户时区的当天算。没配 JEV 密钥就整个跳过，不报错。`MY_DAILY_ENABLED=false` 只关掉 cron 注册，手动「重新评分」和外部 API 触发不受影响。

### 4.2 全局互斥与 FIFO 排队

`acquireScoringSlot` 和 `releaseScoringSlot` 是模块私有函数，没导出。全局同一时刻只允许一个评分任务在跑，不分用户。定时任务、用户手动点「重新评分」、外部 API 触发，共用同一把锁。

重叠触发按 FIFO 排队。名额释放时，`releaseScoringSlot` 直接把名额转交给队首，转交瞬间就写进 `activeScoringJob`，新请求没法插队。

同一 `(userId, date)` 已在执行或排队时，重复触发直接返回 `skipped: reason='duplicate'`。

排队上限 10 个，超出抛 `ScoringQueueError('queue_full')`。最长等 10 分钟，超时抛 `ScoringQueueError('wait_timeout')`。定时任务逐用户串行时也走这把锁，某个用户排队失败只记 warn 并跳过，不中断整轮。

### 4.3 文章级并发

单个用户内按 `MY_DAILY_CONCURRENCY`（默认 5）分批并行调 JEV。每批用 `Promise.all` 等全部完成再进下一批。每篇完成就触发回调，回调里写库并推 SSE。

### 4.4 重试

`callJevApi` 带超时，`JEV_REQUEST_TIMEOUT_MS` 默认 30 秒，用 `AbortController` 实现。最多重试 `JEV_MAX_RETRIES`（默认 2）次，也就是最多 3 次尝试。

可重试的情况：5xx、408 / 429 / 529、网络异常、超时、响应体解析失败。其他 4xx 不重试，直接抛。退避是指数加抖动，1 秒起步，倍数 2，单次上限 30 秒。上游给了 `Retry-After` 就听它的，同样受 30 秒上限约束。

单篇最终失败不阻塞批次，写占位 0 分，最后在 `done` 事件里单独报 `failed` 数。

配置解析失败不算单篇失败。`scoreArticlesBatch` 在批次开始时统一 `resolveJevConfig()`，没配密钥会直接抛异常，整批不执行，不会被降级成单篇 0 分。

`done.scored = inserted - failedCount`。写库失败的条目既不算 `scored` 也不算 `failed`。

## 5. 数据怎么存

`user_daily_scores` 表，见 `sql/044`。

| 字段 | 说明 |
|---|---|
| `user_id` + `article_id` + `score_date` | 联合唯一键，重复评分时 upsert 覆盖 |
| `relevance_score` | 综合评分，REAL，0 到 1 |
| `matched_domain` | 匹配的领域名称，可空 |
| `jev_response` | JEV 原始响应 JSON。成功时是完整响应，失败时是 `{ error: message }` |

`score_date` 是用户时区下的本地自然日，格式 YYYY-MM-DD。查文章时先换算成 UTC 区间再按 `created_at` 过滤。

原始响应完整存进 `jev_response`，方便事后审计和调参。它也是判定该条是否调用失败的持久化依据。

## 6. API 层

### 6.1 内部 API `/api/my-daily`

所有路由都过 `requireAuth` 和 `requireUser`，要求 `role` 是 `user` 或 `admin`，一律按 `req.userId` 过滤，看不到别人的评分。

| 路由 | 方法 | 说明 |
|---|---|---|
| `/api/my-daily?date=` | GET | 查指定日期的评分文章，联表 articles 和 translations。每条带 `failed` 标志和原始 `jev_response`。失败项沉底，其余按分数降序。`date` 缺省是用户时区当天 |
| `/api/my-daily/dates` | GET | 返回 `{ dates, scoredDates, today }`。`dates` 是已有评分的日期并上最近 30 天内有新增文章的日期，去重倒序，上限 30 |
| `/api/my-daily/calendar-status?month=` | GET | 指定月份每日状态，`green` / `yellow` / `orange` / `red` / `future`，带 `hasArticles` / `isScored` / `articleCount` / `failedCount` |
| `/api/my-daily/refresh` | POST | 手动触发当前用户评分。`Accept: text/event-stream` 走 SSE，否则走 JSON。可选 body `date` |

非流式的 `refresh` 有几种返回。`no_topics` 返回 400，引导去配主题。`no_articles` 和 `duplicate` 返回 200，带 message 的 `success: true`。`ScoringQueueError` 返回 429，body 带 `reason`。其余异常返回 500。

SSE 流式评分推三类事件：

| 事件 | 时机 | 载荷 |
|---|---|---|
| `start` | 评分开始 | `{ type, total }` |
| `item` | 每篇出分 | `{ type, current, total, latencyMs?, breakdown?, article: {...} }`。`failed: true` 表示该篇失败，分数是占位 0 |
| `done` | 全部完成 | `{ type, total, scored, failed }` |

另有 `info`（`no_articles` / `duplicate`）和 `error`（未配主题、排队失败带 `statusCode: 429`、JEV 异常）。前端收到 `item` 就插卡片，按分数动态重排。

### 6.2 对外 API `/api/external/my-daily`

给外部项目和 agent 用，鉴权走 `verifyExternalApiAuth`，Header `x-api-key` 或 query `api_key`，对齐服务端 `CLI_API_KEY`，允许 `admin` 和 `user`。响应统一由 `src/api/external-api-response.ts` 包装，字段是 `success` / `code` / `message` / `data` / `meta`。

| 路由 | 方法 | 说明 |
|---|---|---|
| `/api/external/my-daily` | POST | 查询，必要时先触发评分再返回。参数可放 body 或 query |
| `/api/external/my-daily/export` | GET | 全量 JSON 附件导出 |

关键行为：

- 先确保已评分（`ensureScored`）。该日期已有任意一条 `user_daily_scores` 就直接返回缓存，`meta.execution.reason = 'already_scored'`。没有就依次校验「有激活主题领域」（否则 400 `NO_TOPIC_CONFIGURED`）、「已配 JEV 密钥」（否则 503 `JEV_NOT_CONFIGURED`），再 `scoreForUser` 同步跑一遍。成功评分返回 `reason: 'executed'`，无文章返回 `reason: 'no_articles'`。
- 「评分进行中」直接返回 409 `SCORING_IN_PROGRESS`，不写进 `execution.reason`。类型里声明的 `'in_progress'` 目前没有任何代码路径会产生。
- 严格剔除失败占位条目，结果过滤 `article.failed === true`，再按 `minScore` 过滤。
- 分页和裁剪。`limit` 默认 5，上限 100。`offset` 默认 0。`fields` 默认 `core`，不带长摘要，体积小；`full` 带摘要和内部字段。`format=json_file` 直接输出全量 JSON 附件。
- 每条带 `relevance_level`，`high` / `medium` / `low`，阈值 `HIGH_SCORE_THRESHOLD = 0.7`、`MEDIUM_SCORE_THRESHOLD = 0.3`。
- 错误码：日期格式非法 400，主题未配 400，JEV 未配 503，评分进行中 409，排队满或排队超时 429（`retryable: true`），其余 500。

## 7. 前端怎么展示

### 7.1 列表与分档

`my-daily.js` 管页面交互。文章卡片按分数排序，失败项沉底，同分按 id 降序保证稳定。

分档阈值和对外 API 一致：

| 档位 | 阈值 | 展示 |
|---|---|---|
| 高度相关 | score ≥ 0.7 | 正常高亮徽章 |
| 中度相关 | 0.3 ≤ score < 0.7 | 正常徽章 |
| 低相关 | score < 0.3 | low 样式，整卡 `is-low-score` 灰显 |

工具栏统计高、中、低三类数量。三项之和必须等于成功出分的文章数，失败项不计入，不一致时控制台报错。摘要优先显示中文翻译 `summary_zh`，超过 400 字折叠。

### 7.2 实时评分与 FLIP 重排

点「重新评分」后，前端用 `fetch` 读 SSE 流。每收到一个 `item` 就调 `applyFlipSort`，把新卡片插进列表，用 FLIP 动画滑到新位置。动画 240ms，用阻尼曲线。系统开了 `prefers-reduced-motion` 就跳过动画。

HUD（`JevHudController`）是评分时的沉浸式控制台，显示流水线步进、实时概率条、延迟散点、分档分布。失败项不编造延迟，不计入延迟遥测和散点，不参与分档分布。

### 7.3 失败态展示

失败判定统一用 `isJevResponseFailed`。前端不再把占位 0 分当真实低分。

- 文章卡片显示红色「⚠ 评分失败」徽标，不显示 `★ 0%`，整卡加 `is-score-failed` 红边。失败项沉底，不计入分档统计。
- HUD 把失败项标成「调用失败」，状态标签显示「全部失败 (N篇)」或「部分失败 (N篇）」。全部失败时延迟指标显示 `--`。
- 日历组件图例有橙色「评分失败」。某天调了 JEV 但一篇都没拿到真实分数，显示橙色圆点，tooltip 是「JEV 评分失败（N篇），可重新评分」。部分失败仍是绿点。

### 7.4 日历圆点

`calendar-picker.js` 是通用日历选择器，零外部依赖。`showDots` 打开状态圆点。`fetchDotsStatus` 回调去拉 `/api/my-daily/calendar-status`，按 `green` / `yellow` / `orange` / `red` 渲染圆点。后端没就绪时，前端用 `availableDatesSet` 和 `scoredDatesSet` 兜底。

## 8. 配置项

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `TYPESAFE_API_KEY` | 无 | JEV 兜底密钥，优先用 llm_configs 数据库配置 |
| `JEV_REQUEST_TIMEOUT_MS` | `30000` | 单次请求超时 |
| `JEV_MAX_RETRIES` | `2` | 最大重试次数 |
| `MY_DAILY_ENABLED` | `true` | 是否启用定时评分，`false` 只关 cron 注册 |
| `MY_DAILY_SCHEDULE` | `30 7 * * *` | 定时 cron 表达式 |
| `MY_DAILY_CONCURRENCY` | `5` | 单用户内文章并行数 |

JEV 配置解析优先级（`resolveJevConfig`）：先取 `llm_configs` 里 `config_type='jev'` 或 `provider='typesafe'` 且 `enabled = 1` 的配置，按 `is_default desc, priority asc, created_at asc` 取第一条，且 `api_key_encrypted` 能解出密钥。取不到再回退 `.env` 的 `TYPESAFE_API_KEY`。数据库读取失败会降级到环境变量，不抛错。两者都没有才抛错，引导用户去「设置 → LLM 配置」添加。

走数据库配置时，`base_url` 会被 `normalizeJevApiUrl` 归一成 System One endpoint，不以 `/systemone` 结尾就补 `/v1/systemone`，`model` 缺省 `jev-latest`。走环境变量兜底时固定用 `https://api.typesafe.ai/v1/systemone` 加 `jev-latest`。

## 9. 复用到别的项目要注意什么

相关性判断本身只依赖 HTTP 调用，不依赖本仓库的 DB 和调度，可以整段搬走。

| 需要的能力 | 本仓库位置 | 是否自包含 |
|---|---|---|
| 提问拼装（noul / score / choice 加 state 格式） | `src/jev.ts` 的 `buildJevRequest` | 纯函数，未导出，要自己拷或改成导出 |
| 评分公式加 breakdown 加 matched_domain | `src/jev.ts` 的 `calculateScore` | 纯函数，未导出 |
| 超时、重试、Retry-After、退避抖动 | `src/jev.ts` 的 `callJevApi` | 依赖两个 config 常量 |
| 失败占位语义和判定 | `JevScoreResult.failed` 加 `isJevResponseFailed`（已导出） | 自包含 |
| 分档阈值 0.7 / 0.3 | 前端 `my-daily.js` 和 `external-my-daily.routes.ts` 各写一份 | 重复定义，搬运时别漏 |
| 单领域优先加多领域回退 | `resolveArticleTopics` | 强依赖本仓库 5 张源表加 topic 表结构，要按目标项目重写 |

搬走时带上三个已知取舍：

1. 领域归属靠源表绑定（`domain_id`），不靠模型判断。
2. 失败和真实 0 分在 DB 里长得一样，必须靠 `jev_response.error` 区分。
3. 推理耗时没持久化。`latencyMs` 只在 SSE 实时事件里有。刷新页面走 `GET /api/my-daily` 后，HUD 用 `55 + (article.id % 45)` 伪造延迟。要在别的项目展示真实延迟，得自己把 `latencyMs` 一起存下来。

## 10. 和检索精排的同口径实现

`src/vector/jev-reranker.ts`（被 `src/vector/search-service.ts` 用）是同一套相关性公式在检索精排场景的复用。

综合分口径一样：`finalScore = noul × (score / 最高档位)`，0 到 4 五档描述和本模块一致。

差异在提问结构。它把一批候选（`SEARCH_JEV_BATCH`，默认 20）放进同一次请求的 `results[i]` 共享 state，每候选问一对 `r{i}`（noul）加 `s{i}`（score），批级再问一个 `choice` 当「本批是否至少有一条真正涉及该主题」的弃权信号。这和本模块「多领域时用 `best_domain` 做领域归因」的 `choice` 用途不同。

答案解析更保守。`noul` 或 `score` 任一缺失或非有限数就整条丢弃，不像 `calculateScore` 那样兜底成 0 分。

它有独立开关和配额：`SEARCH_JEV_ENABLED`（默认开）、`SEARCH_JEV_BATCH`（默认 20）、`SEARCH_JEV_MAX_CANDERS`（默认 50，源码里就是这个拼写）、`SEARCH_JEV_WEIGHT`。密钥解析是两级，先按 userId 取用户配置，读失败再回退全局 `resolveJevConfig()`，都没有就静默跳过精排，返回 `null`，不影响原排序。
